# Первоначальная загрузка и обмен по событиям

Решение от 5 ноября 2026, ветка `feature/bitrix-initial-sync`. Подтверждённый состав первого импорта — задачи и связанные данные CRM. Почта, записи звонков, календари и интернет-магазин не входят в этот запуск. Первые менеджеры: **Виталий Шевченко** и **Александр Чекальский**; руководители и их реальные внешние ID ещё не подтверждены.

Рабочий портал из этой среды не вызывался. Ключей для реального подключения пока нет. Запись задач в Битрикс и запуск серверных служб автоматически не включаются.

## Порядок работы

```mermaid
flowchart LR
  A[Проверить доступы и тариф] --> B[Подписать приложение на события]
  B --> C[Полная загрузка в архив]
  B --> D[Сохранять изменения в очередь]
  C --> E[Сверить пропуски и применить накопленные изменения]
  D --> E
  E --> F[Подтвердить людей, поля и рабочие связи]
  F --> G[Обновлять конкретные ID из очереди]
```

Подписка нужна **до начала обхода**, иначе изменения во время длительной загрузки могут потеряться. Это не атомарный снимок портала: отдельные карточки читаются в разное время. После обхода очередь перечитывает изменившиеся объекты по ID.

Полный архив хранится отдельно от рабочей модели. Повторный импорт Excel не запускается, существующие 497 задач не заменяются выгрузкой. Архив не назначает администраторами пользователей Битрикса, не угадывает соответствия людей по фамилии, не включает все задачи в исходящую синхронизацию. Для рабочей модели остаются явные сопоставления и активация существующего пилота по [PILOT-LAUNCH.md](PILOT-LAUNCH.md).

Это важная граница текущего выпуска: архив задач/комментариев сам по себе не является автоматическим слиянием всей выгрузки с действующими задачами панели. Публикация компаний в ОКБ подготовлена отдельно, а включение рабочих задач выполняется через существующий проверяемый процесс привязки/выравнивания. Массовое объединение задач с локальными изменениями без сверки не выполняется.

## Состав архива

| Раздел | Что читаем |
|---|---|
| Схемы | Поля задач и основных объектов CRM, реквизитов, адресов, смарт-процессов |
| Сотрудники и структура | Пользователи с доступными стандартными/UF-полями, отделы, проекты и их активные участники |
| Задачи | Все доступные задачи без фильтра по двум менеджерам, статусу или проекту; списочный проход и полная карточка каждого ID; исходные поля, участники, зависимости и CRM-связи |
| Данные задачи | Полная доступная история, результаты с дополнительными данными, чек-листы, затраченное время |
| Обсуждения | Все страницы чата, вспомогательные пользователи и файловые метаданные ответа; для старой карточки — явный режим старых комментариев |
| CRM | Компании ОКБ, контакты, сделки, лиды, связи контактов с компаниями/сделками/лидами, товарные строки сделок/лидов, комментарии таймлайна, дела |
| Справочники | Статусы CRM, реквизиты, банковские реквизиты, адреса, определения и записи смарт-процессов |
| Файлы | Подтверждённые привязки Disk и метаданные, доступные ссылки из ответов; содержимое скачивается в закрытый локальный архив, проверяются размер и SHA-256 |

Исходные JSON сохраняются целиком, включая вложенные и множественные значения. В CRM одного `*` недостаточно для пользовательских/множественных полей: читаются описания полей и запрашиваются их коды. У `crm.item.list` другой контракт: только имена полей или `*`, поэтому неподдерживаемая маска `UF_*` туда не передаётся. Имена UF в смарт-процессах запрашиваются в исходном формате.

Namespace файла нельзя угадывать: ID привязки, объекта Disk и файла из другой подсистемы — разные сущности. Для UF задачи используется `disk.attachedObject.get` → `OBJECT_ID` → `disk.file.get`; для IM — документированные метаданные/ссылка и objectId. Неизвестные файловые привязки и UF-файлы без поддерживаемого способа чтения становятся отдельным незавершённым разделом.

Файлы хранятся в `.local/bitrix-archive` (или `BITRIX_ARCHIVE_DIR`) вне `dist`, каталог 0700, файлы 0600. По умолчанию разрешён файловый хост самого портала; дополнительные **конкретные** доверенные хосты CDN задаются `BITRIX_FILE_HOSTS`. Каждый redirect проверяется заново. Текущий лимит одного файла — 128 МиБ, большой/недоступный файл остаётся явно незагруженным. Ссылки и токены скачивания в журнал не выводятся. Физические файлы не следует коммитить или размещать в публичном каталоге. Для резервного копирования нужен и каталог файлов: обычный дамп PostgreSQL содержит манифест, но не содержимое этих файлов.

## Как защищаем лимиты

Общий PostgreSQL advisory lock и `bitrix_rest_gate` используются панелью обмена, импортом и файловыми загрузками. Нет параллельных серий запросов; минимальный интервал — 1100 мс. Скачивания и redirects тоже резервируют слот. При наличии готовой исходящей работы включённого пилота массовые чтения уступают ей очередь.

Для поддерживающих это методов применяется `ID > последний ID`, сортировка ASC и `start=-1`, чтобы не пересчитывать `total` на каждой странице. Где такого контракта нет, используется документированная пагинация: `START` у отделов, `start` у таймлайна/адресов, `NAV_PARAMS` у учёта времени, `LAST_ID` у IM. IM может вернуть больше LIMIT из-за непрочитанных сообщений, поэтому чтение идёт до пустой страницы с проверкой продвижения курсора.

`time.operating` и `operating_reset_at` сохраняются отдельно по методу. При накоплении 300 секунд действует наш консервативный предварительный порог паузы; это **настройка нашей стратегии, а не универсальное значение тарифа Битрикса**. `OPERATION_TIME_LIMIT` останавливает соответствующий метод, ошибки интенсивности — общую очередь. Задержки повторов чтения растут, курсор при ошибке не сдвигается.

`batch` по умолчанию не применяется: он уменьшает количество HTTP-вызовов, но не отменяет ресурсоёмкость методов и 60-секундный предел запроса. Балансировщик тоже не отменяет лимиты Битрикса. Общая нагрузка других интеграций с того же IP остаётся внешним фактором; нельзя обещать полное отсутствие ответов 429/503. Обработчик должен корректно переживать их, а не пропускать данные.

Первый проход может занять часы: это несколько отдельных чтений на задачу плюс страницы обсуждений, CRM и файлы. Объём и скорость оцениваются после пробного чтения метаданных/размеров, без обещания фиксированного времени.

## События и надёжность

Подписки регистрируются через `event.get` → недостающие `event.bind` → повторная проверка `event.get`. Поддержаны изменения задач, добавление комментариев, создание/изменение/удаление компаний, контактов, сделок, лидов и смарт-объектов, создание пользователя и изменения проектов. Для методов без надёжного события требуется адресная сверка или обновление справочника; обещания событий на каждое поле каждого раздела нет.

Предпочтительный режим — **офлайн-события приложения** с `rest_offline_extended`. Получение — `event.offline.get(clear=0)`. Сначала записываются постоянный inbox и локальная очередь, затем подтверждаются только явно сохранённые `MESSAGE_ID` конкретного непустого `process_id`. Пустые подтверждения запрещены. Неизвестный результат очистки оставляет локальную копию и блокирует готовность; обработка не теряется при перезапуске. Незнакомые зарезервированные пакеты обнаруживаются через недеструктивный `event.offline.list`. `clear=1` не используется.

Офлайн-очередь хранит изменения объектов с объединением, **не полный журнал каждого действия**. Зарезервированный пакет живёт до 30 дней на стороне Битрикса. Поэтому эта очередь обеспечивает актуализацию, а историю надо читать отдельным методом. Повторные уведомления объединяются, generation счётчик не даёт потерять новое изменение, пришедшее во время чтения карточки. Порядку доставки не доверяем: получаем актуальный объект, а не накатываем старые поля события поверх новых.

После включения проверенных подписок прежний периодический обход всех связей прекращается. Исходящий worker обслуживает свои операции; входящий читает указанные ID. Старые `watch` скрипты полного опроса задач/компаний запрещены при активных подписках. Одновременного массового переимпорта на каждое событие нет.

Только сочетание события удаления и подтверждающего чтения с кодом отсутствия отмечается tombstone; история не стирается. Ошибка прав не считается удалением. Для удалённой внешней задачи отключается автоматическая запись. После явной публикации компаний изменения по одному ID обновляют ОКБ; удаление сохраняет карточку, но отключает автоматическое назначение менеджера по ней, восстановление возвращает связь.

Для онлайн-доставки подготовлен `POST /api/bitrix/events`. Обработчик принимает form-urlencoded, сверяет закрытый `application_token`, domain и member_id, записывает событие и отвечает без вызова REST. `auth`, OAuth и refresh-токены входящего payload не сохраняются. Настройка Basic Auth/прокси должна пропускать именно этот endpoint до серверной проверки токена; снимать защиту со всего сайта нельзя. Онлайн-режим не даёт автоматической отметки полной готовности: у Битрикса нет повторной доставки неуспешного онлайн-события.

## Подтверждённые ограничения Битрикса

- `event.bind`, `event.get`, `event.offline.*` требуют контекста **приложения OAuth**. Входящий вебхук для них не подходит (`WRONG_AUTH_TYPE`). Исходящий вебхук настраивается в интерфейсе портала и получает только доступные там онлайн-события.
- Подписки начинают доставлять события только после завершения установки приложения. Режим резервирования/подтверждения зависит от тарифа, проверяется `feature.get(rest_offline_extended)`.
- В новой карточке `tasks >=25.700.0` `OnTaskCommentAdd` передаёт `TASK_ID`, `MESSAGE_ID` и `ID=0`. **OnTaskCommentUpdate/Delete там не работают.** Для изменений/удалений сообщений нужна сверка обсуждения конкретной известной задачи. Перечитанные сообщения обновляются в архиве; неотличимая от утраты доступа/обрезки выдачи пропажа сообщения автоматически не считается достоверным удалением.
- `im.dialog.messages.get` доступен участнику чата. Административный доступ ко всем задачам сам по себе не даёт чтение всех чужих чатов. Отсутствующие права остаются видимым пробелом импорта; добавление людей в чаты ради обхода прав не выполняется.
- REST 3.0 отличается не только путём `/rest/api/`: другие параметры и структура ответа. Одноимённые методы классического API и REST 3.0 нельзя слепо подменять. В архиве используются проверенные классические чтения и IM, работающие с новой карточкой; существующая отправка в task chat остаётся REST 3.0.
- Доступные методы и поля определяются правами токена, scope, лицензией и версией. Частично доступную выгрузку нельзя назвать полным архивом портала. Версии удалённых ранее файлов, недоступные/удалённые до подписки данные и отсутствующая в API история не восстанавливаются искусственно.

## OAuth и конфигурация

Используйте отдельное локальное приложение РУСПЭТ. Не забирать/подтверждать офлайн-очередь чужого приложения: в ней могут быть обработчики другого сервиса. Нужны административная установка, права на task, CRM, пользователей/структуру, проекты, Disk и IM в составе, доступном вашему порталу. Проверка чтения `user.admin` обязательна перед первым обходом; реальные права каждой секции видны по результату чтения. Параметры балансировщика — как в [BITRIX-BALANCER.md](BITRIX-BALANCER.md).

`BITRIX_OAUTH_FILE` указывает на закрытый JSON (0600) вне Git:

```json
{
  "portal": "thebest.bitrix24.ru",
  "member_id": "REPLACE_WITH_CONFIRMED_PORTAL_MEMBER_ID",
  "client_id": "REPLACE_WITH_APP_ID",
  "client_secret": "REPLACE_WITH_APP_SECRET",
  "access_token": "REPLACE_WITH_ACCESS_TOKEN",
  "refresh_token": "REPLACE_WITH_REFRESH_TOKEN",
  "expires": 0
}
```

Это шаблон, а не готовые данные. Access token живёт час, refresh token — 180 дней. Продление обращается к официальному `oauth.bitrix24.tech`, под общей блокировкой приложения и с атомарной записью обеих новых величин. Маркер `.refreshing` создаётся до запроса: если исход неизвестен, повтор блокируется до восстановления авторизации. Не удалять маркер автоматически. При успешном продлении сохраняется новый refresh token, старый не переиспользуется. Файл/каталог должен быть доступен для записи пользователю службы. URL с секретами не выводится в журнал. Реальная регистрация/получение первой пары токенов требуют настройки приложения администратором портала; этот выпуск не содержит публичного установщика/универсального OAuth callback.

Если задан и `BITRIX_WEBHOOK_FILE`, он используется для чтения данных и прежних исходящих операций; для регистрации/получения событий CLI явно использует OAuth. Без вебхука данные тоже можно читать через OAuth. Оба способа делят бюджет одного портала. Для онлайн-событий дополнительно нужен `BITRIX_EVENT_TOKEN_FILE` — отдельный файл application_token события, 0600. В офлайн-режиме публичный callback не требуется.

## Запуск после получения доступов

Сначала основная миграция **021**, затем повторный `scripts/migrate-okb.ts` для отдельной ОКБ. Существующая служба панели и бот должны использовать одинаковый код. Ничего из списка ниже не запускалось на реальном портале в этой облачной задаче.

Из `/opt/ruspet` с окружением нужной службы и под `ruspet`:

```bash
node --import tsx scripts/bitrix-initial-sync.ts selected --actor ID_АДМИНИСТРАТОРА
node --import tsx scripts/bitrix-initial-sync.ts bind --actor ID_АДМИНИСТРАТОРА --confirm
node --import tsx scripts/bitrix-initial-sync.ts start --actor ID_АДМИНИСТРАТОРА --confirm
```

Последняя команда выдаёт UUID загрузки. Далее:

```bash
node --import tsx scripts/bitrix-initial-sync.ts tick UUID --actor ID_АДМИНИСТРАТОРА --steps 10
node --import tsx scripts/bitrix-initial-sync.ts status UUID --actor ID_АДМИНИСТРАТОРА
node --import tsx scripts/bitrix-initial-sync.ts watch UUID --actor ID_АДМИНИСТРАТОРА
```

`--metadata-only` при start создаёт явно обозначенный архив без скачивания содержимого; это не режим «все файлы уже загружены». Pause/resume сохраняют курсоры. `resume UUID --confirm` повторяет ошибочные/заблокированные шаги после исправления доступа. Адресная сверка: `reconcile ID_ЗАДАЧИ --confirm`. Старые карточки выбираются заранее переменной `BITRIX_LEGACY_COMMENTS=true` в окружении импортера.

Статус в панели администратора показывает состав, шаги, ошибки и очередь; отдельные API `/api/system/bitrix-archive` и `/api/system/selected-managers` закрыты от остальных пользователей. `captured` означает завершение обхода, `ready` — отсутствие незавершённых шагов/очередей, подтверждённую офлайн-подписку до старта и выполненную сверку. Наличие archive ready не включает запись в портал.

Компании: `publish-companies UUID --actor ...` показывает план, `--confirm` публикует прочитанные компании в ОКБ и разрешает дальнейшие адресные обновления компаний по событиям. Пакеты идемпотентны, повтор после ошибки допустим, бизнес-статусы/контакты/заметки ОКБ сохраняются. Затем при необходимости `select-managers --actor ... --confirm` сохраняет двух менеджеров после однозначного выбора локальных профилей и подтверждения внешних ID; руководителей не удаляет и пилот не включает.

Для постоянного импортера есть `ops/ruspet-bitrix-import.service`: заранее создать `.local/bitrix-archive` (ruspet, 0700), закрытый `.bitrix-import.env` с `BITRIX_INITIAL_RUN_ID`, `BITRIX_ARCHIVE_ACTOR_ID`, портал/файлы OAuth и транспорта. Служба по умолчанию не установлена и не запущена. При переходе исходящего worker на OAuth переустановить его unit из `ops/ruspet-bitrix-pilot.service`: ему нужен разрешённый путь записи `.secrets` для обновления токенов. После установки unit-файлов требуется `systemctl daemon-reload`. Не включать второй Telegram polling.

Код нужно проверять в изолированной БД: тесты используют вымышленные ответы, отдельный PostgreSQL и временные файлы. Фактические лицензия, права, масштабы, достоверность полного ответа портала и поведение балансировщика проверяются контрольным чтением после получения настроек. Вопросы владельцу балансировщика о REST 3.0 и повторе POST пока остаются открытыми.

Подробная карта официальных источников: [BITRIX-DOCUMENTATION-AUDIT.md](BITRIX-DOCUMENTATION-AUDIT.md).
