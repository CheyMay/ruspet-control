# Битрикс24: двусторонняя синхронизация

Портал: `thebest.bitrix24.ru`. Панель: `https://cheymay.ru`. Код подготовлен, на рабочем сервере не установлен; реальные REST-запросы к порталу и запись в рабочую БД не выполнялись. Нужны миграции 019–021 и новый серверный код, одного dist недостаточно.

## Вебхуки и секреты

Входящий вебхук создаётся в Битриксе с правами **Задачи** (`task`, а для результатов новой карточки также REST 3.0 `tasks`), **Пользователи** (`user`), **Чат и уведомления** (`im`), **Диск** (`disk`) от пользователя, который видит нужные задачи и имеет право их менять. Его полный HTTPS URL сохранить вне Git в `/opt/ruspet/.secrets/bitrix-webhook` (0600).

Исходящий вебхук: `https://cheymay.ru/integrations/bitrix/events`. Выбрать создание, обновление и удаление задачи: `ONTASKADD`, `ONTASKUPDATE`, `ONTASKDELETE`. Также выбрать `ONTASKCOMMENTADD`, `ONTASKCOMMENTUPDATE`, `ONTASKCOMMENTDELETE`: всего шесть событий. В новой карточке изменения/удаления комментариев через старые события не приходят; для них предусмотрены журнал IM и фоновая сверка. Токен приложения сохранить в `/opt/ruspet/.secrets/bitrix-event-tokens` (0600). Для нескольких вебхуков — по одному токену на строку. Не логировать тело запроса: оно содержит токен.

На панели и отдельном обработчике указать:

```dotenv
BITRIX_PORTAL=thebest.bitrix24.ru
BITRIX_EVENTS_ENABLED=true
BITRIX_EVENT_TOKEN_FILE=/opt/ruspet/.secrets/bitrix-event-tokens
BITRIX_WEBHOOK_FILE=/opt/ruspet/.secrets/bitrix-webhook
```

Балансировщик передаёт точный POST-путь `/integrations/bitrix/events` и form-urlencoded тело на панель. Этот путь не требует сессии: приложение проверяет токен и домен. Встроенный viewer-gateway пропускает только этот путь без Basic Auth; остальные пути сохраняют прежнюю защиту. Другой внешний шлюз нужно настроить отдельно.

## Подготовка и начальная загрузка

1. Сохранить защищённую резервную копию рабочей БД и окружения. Установить код и зависимости. Выполнить `npm run db:migrate`. Реальные задачи ради проверки не менять.
2. На этапе загрузки держать `BITRIX_WRITE_ENABLED=false`, `BITRIX_CREATE_ENABLED=false`; отдельный обработчик пока не запускать. Панель с приёмником уже должна принимать события, чтобы изменения во время загрузки сохранились в очереди. Затем сохранить исходящий вебхук в Битриксе.
3. Прочитать HTML .xls в закрытый JSON (файл назначения должен отсутствовать):

```sh
python3 scripts/read-bitrix-export.py <путь-к-xls> --output .local/bitrix-export.json
```

Парсер проверяет ID и столбцы, сохраняет исходные значения и отчёт (0600). Сравнение в отчёте идёт с `data/first-sheet.json`; это ещё не сравнение с рабочей БД. Даты без часового пояса трактуются как МСК. Свежая выгрузка: 388 задач, 327 общих ID с исходными 497, 61 новый, 170 отсутствуют. Отсутствие в файле не считается удалением.

4. До применения файла получить каталог полей командой `metadata` и настроить UF-коды цены/признаков (раздел ниже). Затем прочитать каталог сотрудников и связать нужные имена. До 20 страниц по 50 пользователей, через общий лимитер. Данные в логи не выводятся:

```sh
npx tsx scripts/bitrix.ts export-users .local/bitrix-export.json
```

Автоматически сопоставляются только однозначные полные имена сотрудников из импорта; права существующих аккаунтов сохраняются. Новые сотрудники получают роль employee без назначения руководства и без привязки Telegram. Тёзки требуют явной команды `map-user <локальный ID> <ID Битрикс24>`. Смена уже существующей привязки автоматически запрещена.

5. Подготовить просмотр и применить начальную выгрузку:

```sh
npx tsx scripts/bitrix.ts bootstrap .local/bitrix-export.json
npx tsx scripts/bitrix.ts bootstrap .local/bitrix-export.json --apply
```

Это **нулевые REST-запросы задач**: имена уже сопоставлены, данные берутся из файла. Для существующих исходных ID используется неизменный снимок `imported.initialSnapshot`; правки локальных задач сохраняются, конфликты блокируют применение. Новые задачи получают локальный ID `B-<ID Битрикс24>`. Уже связанные задачи при повторном запуске пропускаются: старый файл не перезаписывает актуальное состояние. Старый импорт Excel поверх рабочей БД запускать нельзя.

6. Закрыть промежуток после выгрузки: читать только задачи, изменённые с указанного времени, по страницам. Время в имени загруженного файла пока трактуется как МСК; если экспорт использовал другой часовой пояс, передать фактическое время (можно раньше с запасом):

```sh
npx tsx scripts/bitrix.ts catchup '2026-11-12T10:22:35+03:00' 0
```

Команда читает максимум 10 страниц за проход, не делает отдельный GET каждой задачи и ничего не отправляет в Битрикс. При `complete:false` продолжить с показанного cursor вместо 0. Приём событий должен работать до начала этого прохода; более поздние изменения обработает очередь. Ошибки/конфликты нужно разобрать до массовой обратной записи.

## Постоянный обработчик

Для двусторонней работы на единственном обработчике:

```dotenv
BITRIX_WRITE_ENABLED=true
BITRIX_IMPORT_NEW_ENABLED=true
BITRIX_CREATE_ENABLED=true
BITRIX_CONTENT_ENABLED=true
BITRIX_RECONCILE_ENABLED=true
BITRIX_UPLOAD_FOLDER_ID=<реальный ID доступной папки Диска>
```

`BITRIX_IMPORT_NEW_ENABLED` импортирует новые задачи из входящих событий в пределах видимости пользователя вебхука. Не настраивать вебхук от аккаунта с более широкой областью, чем требуется приложению. `BITRIX_CREATE_ENABLED` разрешает создание локальных задач в Битриксе; нужны привязки исполнителя и постановщика. На панели/боте эти флаги не запускают синхронизацию сами.

Запустить из каталога приложения отдельную службу:

```sh
npx tsx scripts/bitrix.ts events
```

Она последовательно обслуживает входящие сигналы задач/комментариев, создание, комментарии и результаты, изменения связанных разделов, локальную очередь, фоновую сверку карточек и ограниченный catchup. Общая advisory-блокировка 431025 запрещает одновременный watch/второй экземпляр/ручные команды. Перед ручной командой остановить эту службу. Панель и Telegram остаются на общей PostgreSQL; новый Telegram polling не запускается.

Повторные события объединяются по ID. HTTP 202 выдаётся после записи в БД. Перезапуск сохраняет очередь; событие, пришедшее во время сверки, остаётся для следующего прохода. Служебное соединение REST и постоянных отметок попыток отделено от пула транзакций панели/бота, чтобы ожидающие запросы не создавали взаимную блокировку. Общий REST-лимитер для всех процессов на этой БД допускает один запрос за раз с интервалом 1,1 секунды, паузами после ограничений и повторами с задержкой до часа.

## Поля, конфликты и неизвестный результат

В обе стороны: название, описание, крайний срок (включая снятие), исполнитель, постановщик, статус. Локальные active/review/completed соответствуют 2/4/5; входящие 2/3/6 представлены как active. Если локальный статус не менялся, исходные 3/6 обратно в 2 не перезаписываются. Для входящего завершения дата берётся из `closedDate`, не выдумывается. Также поддержаны плановые даты, приоритет, соисполнители и наблюдатели. Участники получают доступ к соответствующей локальной задаче без назначения управленческих ролей. Цена и признаки важности/риска требуют реальных UF-кодов через field-map. Произвольные локальные поля сопоставляются по однозначному названию с существующими UF-полями из метаданных, включая создание задачи. Отсутствие соответствия или подтверждённого значения блокирует отправку; операция не считается успешно отправленной. Создание новых определений UF-полей на портале автоматически не выполняется.

Для записи проверяются права вебхука самим REST, выполняются чтение, повторная сверка непосредственно перед обновлением и контрольное чтение результата. Если Битрикс игнорирует статус или поле, локальная операция не помечается отправленной. Параллельные правки одного поля блокируются. У REST нет условной атомарной записи по версии, поэтому полностью исключить внешнюю правку в промежутке между проверкой и записью нельзя; этот сценарий нужно проверить на портале перед массовым включением. Статусы/права/настройки контроля также требуют реальной проверки.

Создание имеет постоянный журнал намерения и `XML_ID=ruspet:<operation_key>`. Неизвестный результат создания не вызывает повторного ADD. При состоянии uncertain найти созданную задачу на портале и подтвердить её ID:

```sh
npx tsx scripts/bitrix.ts confirm-created <локальный ID> <ID созданной задачи Битрикс24>
```

Команда проверяет совпадение XML_ID; обработчик затем перечитает задачу и привяжет её. Если задачи на портале нет, требуется ручной разбор попытки перед повтором — автоматического удаления намерения нет. Правка локальной задачи во время создания сохраняется в очереди до следующей отправки.

Событие удаления сначала проверяется REST-чтением: существующая/восстановленная задача не архивируется из-за запоздавшего события. Подтверждённый ERROR_TASK_NOT_FOUND помечает конфликт, убирает задачу из активных списков/напоминаний и останавливает обратную отправку; данные и история остаются в архиве администратора `/api/integrations/bitrix/deleted`. Доступность восстановленной задачи перечитывается, признак архива снимается. Ошибка прав не считается подтверждением удаления. Локальное удаление в Битрикс не отправляется.

## Комментарии, результаты, файлы и чек-листы

Комментарии Битрикса сохраняются в общем обсуждении панели и бота с настоящим автором и датой. `TASK_ID` — ID задачи, `ID` — старого комментария, `MESSAGE_ID` — сообщения новой карточки, где старый ID может быть 0. Входящие сообщения не создают обратного эха. Изменения и удаления сохраняют прежний текст в журнале; удалённые записи скрываются из текущего обсуждения, а не стирают историю.

Все новые локальные комментарии, включая сдачу, возврат, уточнения и обсуждение согласований, транзакционно ставятся в отдельную очередь. В Битрикс отправляется текст с подписью настоящего локального автора; технический аккаунт не выдаётся за сотрудника. Для новой карточки используются `im.message.*`, для проверенной старой — `task.commentitem.*` с `BITRIX_LEGACY_COMMENTS=true`. Битрикс разрешает менять в чате только свои сообщения и в пределах своего срока редактирования (по документации — 3 суток); ограничения сервера не обходятся, ошибка остаётся видимой. Принудительно изменить чужой комментарий через один вебхук нельзя.

Комментарии можно редактировать/удалять из панели с проверкой автора/прав и revision. После начала внешней отправки обычная пятиминутная отмена создания комментария запрещается; используется явное удаление, также с очередью. Неизвестный результат ADD не повторяется. После сбоя процесс помечает незавершённые создания как uncertain. Для подтверждения уже отправленного комментария:

```sh
npx tsx scripts/bitrix.ts confirm-comment <локальный UUID комментария> <ID сообщения Битрикс24>
```

Команда проверяет задачу, ID и точное совпадение отправленного текста. Локальная правка, сделанная во время отправки, сохраняется для следующего прохода. Для старых локальных комментариев, существовавших до миграции, отдельно доступны `comments-backfill` (сначала счётчик) и `comments-backfill --apply` (постановка в очередь); массовая отправка старого обсуждения автоматически не включается.

Текст сдачи закрепляется как результат из отправленного комментария, затем передаётся статус. Используются старый addFromComment или REST 3.0 addfromchatmessage по типу карточки. Перед добавлением проверяются уже существующие результаты; для REST 3.0 передаётся постоянный Idempotency-Key. Исторические результаты, уже удалённые из Битрикса до подключения и недоступные через API, не выдумываются.

В карточке панели появились связанные разделы: поля/участники, чек-листы, файлы, результаты и история. Дополнительные поля можно менять по реальному каталогу; создание/изменение/удаление пунктов чек-листа проверяет текущий снимок и конфликт на портале. В боте доступны общее обсуждение и раздел чек-листов, файлов и результатов, включая отметку пункта чек-листа. Полный набор форм редактирования и загрузка файлов находятся в панели.

Файл до 10 МБ загружается в настроенную папку Диска, затем прикрепляется к задаче и перечитывается. Неизвестный результат загрузки не повторяется вслепую. Удаление вложения убирает связь с задачей; исходный файл на Диске не уничтожается. Скачать можно также вложения комментария: сервер проверяет права на задачу и актуальную связь с задачей/сообщением. Подписанные download/preview URL не хранятся в снимках и не выдаются в API. Скачивание до 64 МБ проксируется с портала; дополнительные точные доверенные хосты хранилища задаются в `BITRIX_FILE_HOSTS` через запятую. Каждый redirect проверяется, посторонние хосты отклоняются.

### Метаданные и цена

До начальной загрузки получить реальный каталог полей:

```sh
npx tsx scripts/bitrix.ts metadata
```

Затем сопоставить известные локальные поля с существующими кодами из каталога:

```text
npx tsx scripts/bitrix.ts field-map price <реальный UF-код цены>
npx tsx scripts/bitrix.ts field-map important <реальный UF-код важности>
npx tsx scripts/bitrix.ts field-map customer_risk <реальный UF-код риска>
```

Это проверяет существование кодов; значения перечислений/тип поля необходимо сверить на портале, а не считать любое перечисление логическим признаком. Изменённое локальное поле без сопоставления не помечается отправленным. Сам каталог доступен администратору/участнику в данных карточки без секретов.

### Нагрузка и журнал IM

Секции карточки обновляются постепенно: не чаще одного фонового шага в 15 секунд, один раздел одной задачи за шаг. Для файлов фоновый шаг читает максимум три вложения; для обсуждения — одну страницу и максимум два контрольных чтения старых сообщений. «Обновить из Битрикс24» ставит выбранную карточку в приоритет. Все REST-вызовы идут через тот же общий лимитер. Входящие события и локальная отправка имеют приоритет перед очередным фоновым шагом. Начальная загрузка всей старой переписки/файлов занимает время, она не выполняется одним массовым проходом.

Обсуждение хранит отдельно курсор старой истории и последнего нового сообщения. После простоя читаются следующие новые сообщения через FIRST_ID; поток больше 50 сообщений не обрезается последней страницей. Изменения старых сообщений также перепроверяются постепенно. Без журнала IM обнаружение старого редактирования/удаления может занимать полный цикл контрольных чтений.

Для быстрого получения новых, изменённых и удалённых сообщений новой карточки используется `im.v2.Event.subscribe/get`. **Очередь общая для пользователя Битрикса; offset удаляет события также у других приложений.** Включать только для отдельного пользователя интеграции, у которого нет другого потребителя этой очереди:

```dotenv
BITRIX_IM_EVENTS_EXCLUSIVE=true
```

По умолчанию выключено. Подписанный пользователь должен состоять в нужных чатах задач. События хранятся на стороне Битрикса 24 часа. Курсор подтверждается следующим сетевым запросом только после локального COMMIT; чужие личные чаты не копируются. После длительного простоя остаётся фоновая сверка. Изменения, сделанные сторонним `im.message.update`, могут не порождать IM-событие по контракту API; контрольные чтения для этого сохраняются.

## Контроль

Администратору доступен `GET /api/integrations/bitrix/events`: очередь, ошибки обратной отправки, неподтверждённые создания, heartbeat и флаги единственного обработчика, время приёма и обработки, без секретов. Heartbeat пишется каждые 15 секунд; отсутствие больше 45 секунд даёт workerActive=false. С `BITRIX_RECONCILE_ENABLED=true` каждые 30 минут проверяются только изменённые задачи по CHANGED_DATE: одна страница за шаг, курсор сохраняется в БД, окно имеет перекрытие 5 минут. На первом проходе по умолчанию берутся последние сутки; первичную загрузку и catchup от времени выгрузки это не заменяет. Нельзя считать принятый хук доказательством успешного применения задачи.

После отключения импортирования новых задач их события остаются заблокированными. После разрешённой привязки их можно переоткрыть в административном SQL-сеансе:

```sql
UPDATE bitrix_event_queue q SET blocked=false, processed_at=NULL, available_at=now(), last_error=NULL
WHERE q.blocked AND q.event<>'ONTASKDELETE'
AND EXISTS(SELECT 1 FROM bitrix_task_links l WHERE l.external_id=q.external_id);
```

Официальные источники: [обновление](https://apidocs.bitrix24.ru/api-reference/tasks/tasks-task-update.html), [создание](https://apidocs.bitrix24.ru/api-reference/tasks/tasks-task-add.html), [список задач](https://apidocs.bitrix24.ru/api-reference/tasks/tasks-task-list.html), [поля](https://apidocs.bitrix24.ru/api-reference/tasks/fields.html), [сотрудники](https://apidocs.bitrix24.ru/api-reference/user/user-get.html). Для разработки сверены соответствующие страницы официального репозитория bitrix-tools/b24-rest-docs.
