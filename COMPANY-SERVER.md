Владелец выбрал сервер `194.226.98.113`, новый домен `ruspetdev.ru`. Подтверждено через PuTTY: Ubuntu 24.04.5 amd64, RAM 1.9 GiB/доступно 1.5 GiB, диск 30 GiB/свободно 23 GiB, swap отсутствует. На 3000 работает docker-proxy; Node/npm/PostgreSQL/Nginx на хосте отсутствуют. SSH слушает 0.0.0.0:22 и [::]:22. Docker и его приложение не удалять и не перенастраивать.

Агент напрямую к VPS не подключён: попытки SSH получили Connection refused до аутентификации. Проверка действующей политики облачной среды показала TCP enabled=false и отключённый Tailscale. Это не доказывало отсутствие SSH на VPS; после проверки владелец вошёл через PuTTY. Установку выполняет владелец вставкой блоков в PuTTY. Присланный приватный RSA-ключ хранится только в игнорируемой .local, в Git/команды/вывод не включать. Прямая root-аутентификация этим ключом не проверена.

## Подготовка

Скрипт `scripts/prepare-company-server.sh` подготовлен именно под эту Ubuntu/архитектуру. Запускать от root, весь процесс ограничивать CPU, как ниже:

```bash
systemd-run --scope --quiet -p CPUQuota=60% nice -n 10 bash /root/ruspet-prepare.sh
```

Содержимое `/root/ruspet-prepare.sh` — точная копия `scripts/prepare-company-server.sh`. Устанавливает официальные NodeSource 22.x и PostgreSQL PGDG 17, Nginx/Certbot, Git/rsync и инструменты сборки. Использует HTTPS и отдельные signed-by keyrings, не выполняет скачанные shell-скрипты. Добавляет 2 GiB swap при отсутствии swap и файла /swapfile, сохраняя fstab. Создаёт ruspet и пустую ruspet_demo, не очищает существующие БД. Подготавливает /root/ruspet-code и /opt/ruspet, закрытые .local/.secrets. Генерирует отдельный GitHub deploy key при отсутствии, выводит только public key; известные хост-ключи GitHub берёт из публичного HTTPS API. App/bot/Bitrix ещё не запускаются; конфигурация firewall/SSH authentication/Docker не меняется. До переноса Nginx показывает стандартный стартовый сайт.

В GitHub CheyMay/ruspet-control → Settings → Deploy keys добавить выведенный **публичный** ключ с доступом только чтения. После этого можно клонировать с тем же GIT_SSH_COMMAND и путём ключа, что в прежнем updater. Приватный ключ из /root/.ssh не копировать в чат.

## Перенос действующей системы

Домен: A @ → 194.226.98.113. У корня удалить прежние парковочные A/AAAA, если они уводят запросы на другие адреса. IPv6 пока не публикуется. TLS выпускать после проверки DNS и HTTP-доступности домена. Финальный PUBLIC_ORIGIN=https://ruspetdev.ru.

Авторитетные данные — на прежнем VPS /opt/ruspet, а не исходная выгрузка/Git. Перед переносом сверить реально установленный commit и актуальные изменения других веток. Сохранить core dump ruspet_demo, отдельный ruspet_okb если настроен, приватные .env/.telegram-worker.env/.secrets/.access и нужные .local/Bitrix-файлы с правами 0600/0700. Секреты передавать через SSH/SFTP, не через чат/Git. Созданный локальный role ruspet не имеет пароля: для целевой конфигурации выбрать Unix peer или отдельно настроить закрытые пароли, а DATABASE_URL/OKB_DATABASE_URL адаптировать. pg_dump не переносит роли и их пароли. Восстановить снимок на целевом сервере и проверить количества задач/пользователей/согласований/справочника, не выполнять повторный seed.

Для финального снимка остановить запись старой панели и единственный старый polling-worker, затем восстановить данные на новом сервере. Панель запускается от ruspet, 127.0.0.1:4310, DEMO_AUTH=false, TELEGRAM_WORKER_DISABLED=true. Отдельный единственный worker использует прежний рабочий HTTPS-мост с body-форматом, тот же PostgreSQL и отдельное окружение. До остановки прежнего worker целевой не запускать: advisory lock между разными БД не защищает от двух polling-копий. Входящие/исходящие Bitrix workers по умолчанию не активировать; готовность и внешние ID ещё требуют подтверждения.

Порядок завершения: код/зависимости → восстановление и миграции → панель и локальный health → Nginx под домен → DNS/HTTPS → один worker → пароль/QR/свой /menu → резервное копирование с контрольным восстановлением. Существующие аккаунты, роли, задачи, история и справочник сохраняются. На момент подготовки скрипта выполнение на новом сервере ещё не подтверждено.
