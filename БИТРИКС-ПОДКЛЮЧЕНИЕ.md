# Подключение Битрикс24

## Задачи из Битрикс24 в РУСПЭТ

Рабочий портал — thebest.bitrix24.ru. В разделе «Разработчикам → Другое → Исходящий вебхук» укажите обработчик [ruspetdev.ru/api/bitrix/events](https://ruspetdev.ru/api/bitrix/events). Выберите события задач `OnTaskAdd`, `OnTaskUpdate`, `OnTaskDelete` и `OnTaskCommentAdd`, доступные в списке портала. Сохраните токен приложения этого вебхука.

Для чтения нужен отдельно созданный входящий вебхук с доступом к задачам сотрудников. Для сверки участников нужен `user_brief`, для чтения новых чатов — `im` и доступ учётной записи к чату. Для REST используется балансировщик Романа. Запись в портал в этом режиме отключена.

На рабочем VPS под root введите настройки. Значения считываются скрыто, файлы создаются с правами 0600.

```bash
bash /opt/ruspet/scripts/configure-bitrix-inbound.sh
```

Проверьте чтение одной задачи из выгрузки, затем включите обработчик. Указанные сервисы и drop-in должны относиться к рабочему РУСПЭТ на `194.226.98.113`.

```bash
systemd-run --quiet --wait --pipe --collect -p User=ruspet \
  -p WorkingDirectory=/opt/ruspet -p EnvironmentFile=/etc/ruspet/bitrix-inbound.env \
  /usr/bin/node --import tsx scripts/bitrix-inbound.ts verify --id ID_ИЗ_ВЫГРУЗКИ
```

Для панели подключите `/etc/ruspet/bitrix-inbound.env` как последний `EnvironmentFile`. После перезапуска панели выполните в том же окружении команду `prepare`. Она настраивает приём событий. Первое событие с верным токеном закрепит идентификатор портала. Установите и запустите `ops/ruspet-bitrix-inbound.service`. Для первой сверки используйте `enqueue --id ID_ИЗ_ВЫГРУЗКИ`, после проверки запустите `enqueue` для всех задач из выгрузки. `status` показывает количество обработанных, ожидающих и заблокированных задач. Перед массовой сверкой сохраните резервную копию рабочей базы.

Сверка обновляет задачи из выгрузки по подтверждённым ID, сохраняет историю и локальные правки. При расхождении одного поля оно остаётся на сверку. Назначения проверяются по уже подтверждённым связям или по ID из справочника и имени из API. Новые задачи вне текущего набора пропускаются до согласования границ импорта. Неполный ответ, отсутствие прав и неподдерживаемый статус не удаляют локальную задачу. Комментарии по новым событиям сохраняются отдельно, полный архив прошлых обсуждений загружается отдельным прогоном. При первом выравнивании срока исторические переносы не начисляются.

Справка Битрикс24 о настройке вебхуков и структуре событий. [Входящие и исходящие вебхуки](https://apidocs.bitrix24.ru/local-integrations/local-webhooks.html) · [События задач](https://apidocs.bitrix24.ru/api-reference/tasks/events-tasks/index.html)

## Состояние на 13 ноября

В РУСПЭТ есть REST-клиент, транспорт через балансировщик, архив чтения, привязки людей и задач, очередь обмена и панель её состояния. На рабочем VPS вебхук и настройки балансировщика ещё не установлены. Обмен выключен, сопоставлений и активированных задач нет. Вебхуки на стороне портала, по данным владельца, подготовлены.

Используем балансировщик, который передал Роман. Он подписывает запрос на стороне клиента по HMAC и проксирует запрос в портал. В РУСПЭТ остаются локальная очередь, сверка и лимит запросов к порталу. Мост для Telegram и прокси Groq работают отдельно.

## Порядок подключения

1. На VPS записать рабочий входящий вебхук в `/opt/ruspet/.secrets/bitrix-webhook`, параметры балансировщика в `/opt/ruspet/.secrets/bitrix-balancer.json`. Владелец файлов `ruspet`, права `600`. Пример формы файла есть в [BITRIX-BALANCER.md](BITRIX-BALANCER.md).
2. В доверенном окружении CLI и обработчика указать `BITRIX_PORTAL`, `BITRIX_WEBHOOK_FILE`, `BITRIX_TRANSPORT=balancer`, `BITRIX_BALANCER_CONFIG_FILE`. Оставить `BITRIX_WRITE_ENABLED=false` на первом прогоне. Проверить часы сервера и HTTPS шлюза.
3. Из `/opt/ruspet` выполнить `runuser -u ruspet -- node --import tsx scripts/bitrix-pilot.ts fields`. Это чтение каталога полей через выбранный транспорт. Сверить проект, точный код поля цены, права технической учётной записи, чтение комментариев и режим чата.
4. Подтвердить ID пользователей портала и связать исполнителей, постановщиков и руководителей. Указать состав пилота, проект и поле цены. На первом прогоне выбрать одну существующую задачу, связать ID и посмотреть расхождения. Затем активировать её связь по [PILOT-LAUNCH.md](PILOT-LAUNCH.md).
5. При необходимости перенести исходное состояние через возобновляемый архив и сверку. Отдельно проверить старые комментарии, историю и переносы, которые отсутствовали в Excel. Для событий выбрать поддерживаемый вариант из [BITRIX-BOOTSTRAP.md](BITRIX-BOOTSTRAP.md). Входящий вебхук для REST и регистрация событий — разные настройки.
6. После согласования с владельцем выполнить контрольную запись на выбранной задаче. Проверить комментарий в обе стороны, перенос через согласование, сдачу, возврат и закрытие. Подтвердить, что новый чат REST 3.0 проходит через шлюз. Включить рабочую очередь только после этих проверок.
7. Следить за очередью и ограничением до двух запросов в секунду. Если ответ на запись потерян, сначала сверить состояние в портале. Для комментария искать маркер операции. Кнопка «Пауза» оставляет операции в очереди.

Для согласованных связей поддерживаются изменение названия, описания, цены, исполнителя, срока, статусов и отправка текста в обсуждение. Создание задач, копий и поручений на портале пока за пределами обмена. Эти объекты создаются в РУСПЭТ.
