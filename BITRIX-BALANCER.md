# Транспорт через балансировщик Битрикс24

Ветка `feature/bitrix-balancer` включает выпуск подготовки пилота. Протокол перенесён из предоставленного `balancer-example.js`; сам файл с его URL/ключами в Git не добавляется и не исполняется. Пример использует Google Apps Script (`Utilities`, `UrlFetchApp`), а приложение — Node.js.

В переданном примере адрес вебхука содержит шаблонные части вместо рабочего числового ID пользователя и токена. Перед подключением нужен корректный вебхук нужного портала. Проверка не подменяет неизвестные значения вымышленными.

## Протокол

- POST на настроенный HTTPS endpoint шлюза.
- Подпись: HMAC-SHA256 от строки `publicKey:timestamp`, ключ — буквальная UTF-8 строка `privateKey`. Результат — 64 строчные hex-цифры. Timestamp — Unix-секунды.
- Заголовки `X-Timestamp` и `X-Signature`; тело `{url, method: 'POST', body: params}`.
- Для классического REST к URL метода добавляется `.json`, как в примере. Для REST 3.0 сохраняется документированный путь `/rest/api/…` без добавления `.json`. Поддержку такого пути самим шлюзом ещё должен подтвердить его владелец.
- Успешный одиночный ответ шлюза ожидается как `{body: <исходный REST-ответ>}`. `result`, `error`, `next` внутри этого ответа сохраняются при распаковке. Внутренний клиент по-прежнему получает Bitrix `result`; существующие сканеры используют ограниченные страницы/курсор.
- Рекуррентный режим `is_recurrent` / `result_key` пока не используется: для пилота сохраняются контролируемая пагинация и ограничения выборки. Формат частичного ответа, пределы объёма и значение квот нужно уточнить.
- Локальная последовательная очередь, общий лимитер и сверка результата сохраняются. Квота шлюза пока не меняет локальную скорость автоматически — её область действия неизвестна.
- Нет автоматических повторов и переключения на прямой доступ при ошибке шлюза. Повторы в присланном примере не перенесены. Неизвестная отправка обрабатывается очередью как неопределённая. Внутренние повторы самого шлюза и поддержка идемпотентности остаются вопросами к владельцу.
- Авторизация шлюза (401/403), его HTTP-ошибки и вложенная ошибка Bitrix различаются. Необработанное содержимое ошибки, ключи, подписи и URL вебхука не печатаются.

## Закрытая конфигурация

После установки кода в `/opt/ruspet/.secrets/bitrix-balancer.json`, права `600`, владелец `ruspet`:

```json
{
  "url": "https://BALANCER_HOST/ENDPOINT",
  "publicKey": "PUBLIC_KEY",
  "privateKey": "PRIVATE_KEY"
}
```

Это схема с заменяемыми значениями, не реальные настройки. URL может содержать служебные параметры, поэтому весь файл считается секретом. Вебхук хранится отдельно в `/opt/ruspet/.secrets/bitrix-webhook`, как описано в [PILOT-LAUNCH.md](PILOT-LAUNCH.md).

В окружении панели/работающего Bitrix worker:

```dotenv
BITRIX_PORTAL=thebest.bitrix24.ru
BITRIX_WEBHOOK_FILE=/opt/ruspet/.secrets/bitrix-webhook
BITRIX_TRANSPORT=balancer
BITRIX_BALANCER_CONFIG_FILE=/opt/ruspet/.secrets/bitrix-balancer.json
BITRIX_BALANCER_TIMEOUT_MS=60000
```

Установленная переменная `BITRIX_BALANCER_CONFIG_FILE` также выбирает балансировщик по умолчанию, если режим не указан. Явное `BITRIX_TRANSPORT=direct` оставляет прямой доступ. Автоматического обхода балансировщика нет. Некорректная конфигурация выбранного шлюза останавливает клиент. Таймаут настраивается от 1 до 120 секунд; время очереди/работы шлюза ещё нужно уточнить. Сначала не включать запись (`BITRIX_WRITE_ENABLED=false`).

Если доверенный пример с уже заполненным рабочим вебхуком сохранён на VPS в закрытом файле, можно извлечь четыре константы без запуска его кода:

```bash
cd /opt/ruspet
install -d -m 700 -o ruspet -g ruspet /opt/ruspet/.secrets
runuser -u ruspet -- npx tsx scripts/import-balancer-example.ts /opt/ruspet/.secrets/balancer-example.js
```

Исходный файл тоже должен быть доступен `ruspet` и закрыт от других пользователей. Без `--apply` показываются только план и пути. Для создания файлов повторить с `--apply`. Файлы создаются с правами `600`; идентичные существующие настройки сохраняются, отличающиеся не перезаписываются. Код с переменными/выражениями вместо четырёх строковых констант отклоняется. Шаблонный вебхук из исходного примера также отклоняется. Секретные значения не выводятся. Транспорт сам собой не включается.

После настройки выполнить чтение каталога полей через `scripts/bitrix-pilot.ts fields` с тем же окружением, что у worker. Это проверка чтения, она не меняет задачи. После смены транспорта нужно выполнить её заново, а не полагаться на старый heartbeat REST. Затем проверить права, REST 3.0 и контрольную запись по плану пилота. Новая миграция для транспорта не требуется; миграция 019 выпуска пилота остаётся обязательной.

## Вопросы владельцу шлюза

1. Поддерживаются ли REST 3.0 `/rest/api/…` и методы чата задач? Нужен ли для них `.json`?
2. Повторяет ли шлюз POST при таймаутах/ошибках? Поддерживает ли ключ операции, дедупликацию или проверку статуса запроса после потери ответа?
3. Ответ означает завершённый вызов Bitrix или только постановку в очередь? Каковы допустимое время ожидания и точная схема ошибок/исходного HTTP-статуса?
4. Как действуют общие лимиты, параллелизм, `quota_left` и `Retry-After`? Они относятся к порталу, клиенту или всей системе?
5. Срок действия подписи/допуск часов, необходимость отдельной пары ключей и IP whitelist? Кто выдаёт рабочий вебхук и какие права/области у него должны быть?
6. Каковы точный формат рекуррентного ответа, смысл `result_key`, пределы страниц/объёма и признак неполной выгрузки/продолжения?

Реальные ключи и URL в вопросах не приводить. Вопросы формулируют недостающие условия, а не предполагают их поддержку.
