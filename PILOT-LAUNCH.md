# Первый рабочий пилот · 5 ноября 2026

Портал: `thebest.bitrix24.ru`. Владелец подтвердил установку входов сотрудников и палитр. Имена двух менеджеров и руководителей, ID проекта, вебхук и техническое поле цены пока не предоставлены. Обмен с реальным порталом из облака не выполнялся. До настройки и контрольного прогона выпуск не следует считать запущенным в работу.

## Возможности и границы этого выпуска

- Получение всех стандартных полей через `select: ['*', …]`, явное добавление пользовательских UF-полей из `tasks.task.getFields`, включая сведения о CRM/файлах. Неизвестные поля и вложенные значения сохраняются полностью в отдельном исходном снимке. В карточке доступен раздел «Все полученные поля Битрикс24».
- Комментарии и история читаются отдельно, с доступной пагинацией. Скачивание содержимого файлов, вложения комментариев, удалённые сообщения и восстановление всей прошлой истории в этом выпуске не реализованы. Идентификатор файла не означает, что его содержимое уже скопировано.
- Для явно включённых существующих задач: название, описание, цена, исполнитель, крайний срок и переходы работа → приёмка → завершение / возврат. Приёмка остаётся в нашей системе; Битрикс получает результат решения. Новое значение срока сохраняется после действующего согласования.
- Обсуждение, объяснения и решения отправляются в чат задачи с именем сотрудника в тексте и маркером операции. Автор на портале — учётная запись вебхука; система не подделывает автора.
- REST 3.0 для нового чата: `tasks.task.chat.message.send`, адрес `/rest/api/…`. Для старой карточки есть явный `BITRIX_LEGACY_COMMENTS=true` с `task.commentitem.add`; автоматического переключения после ошибки нет.
- Локальная запись и очередь операции атомарны. Работает один последовательный обработчик с общим лимитером REST. Старые mock-операции не проигрываются в портал. Очередь создаётся только для новых действий после включения конкретной связи.
- Перед записью выполняется сверка изменяемых полей, после — контрольное чтение. Независимые изменения портала сохраняются. При конфликте останавливается соответствующая задача. Неизвестный результат не повторяется автоматически, особенно отправка комментария.
- В боте и панели показано: только локально, чтение, приостановлено, очередь, отправка, ошибка, конфликт или последняя подтверждённая сверка. Администратор видит проверку готовности и очередь в настройках.
- **Создание новых задач/поручений и произвольная запись всех полей Битрикс24 пока не реализованы.** Новые локальные задачи явно обозначаются как локальные. Нативный объект результата Bitrix24 и вложения результата не создаются: результат передаётся текстом комментария; ограничения завершения конкретного портала нужно проверить контрольным прогоном. Для первого пилота выбираются существующие связанные задачи. Прочие полученные поля доступны для чтения; внутренние поля РУСПЭТ не объявляются синхронизированными с порталом. Включённые расписания/бизнес-процессы не превращаются автоматически в интеграцию создания задач.

## 1. Что нужно от администратора портала

Создать технический входящий вебхук с доступом к выбранному проекту, редактированию его задач, сотрудникам и обсуждениям. Для классических методов нужны соответствующие права `task`, `user`, `im`; новый чат использует REST 3.0 и scope `tasks`. Доступность методов и прав проверяется на реальном портале до допуска участников. Для приёмки/возврата технической учётной записи нужны права постановщика или администратора задачи. Не выдавать участникам общий admin/director вместо персональных профилей.

URL вебхука записать **только на VPS** в `/opt/ruspet/.secrets/bitrix-webhook`, файл принадлежит `ruspet`, права `600`. В Git/чат/командные аргументы URL не помещать. В окружении указать:

```dotenv
BITRIX_PORTAL=thebest.bitrix24.ru
BITRIX_WEBHOOK_FILE=/opt/ruspet/.secrets/bitrix-webhook
BITRIX_WRITE_ENABLED=false
BITRIX_LEGACY_COMMENTS=false
```

Цена не определяется по догадке или названию поля. Получить каталог:

```bash
cd /opt/ruspet
runuser -u ruspet -- npx tsx scripts/bitrix-pilot.ts fields
```

Выбрать точный код обязательного поля цены, проверить тип и рубли. При денежном формате поддержано `сумма|RUB`. Другие валюты не пересчитываются молча.

## 2. Установка выпуска

Нужны Node.js ≥22.12, код ветки `feature/pilot-readiness`, зависимости lockfile и миграция `019_bitrix_live_pilot.sql`. Миграция не включает обмен и не изменяет 497 исходных задач.

1. Сделать свежий защищённый дамп PostgreSQL и копию кода/окружения. Старую базу не заменять выгрузкой; `db:seed` не запускать.
2. В отдельной Git-копии получить ветку и выполнить последовательно `npm ci --include=dev`, `npm run check`, `GOMAXPROCS=1 npm run build`.
3. Остановить `ruspet.service`, `ruspet-bot-proxy.service` и прежний Bitrix watch, если он запускался. Обновить полный код `/opt/ruspet` (в том числе `server`, `shared`, `scripts`, `web`, `ops`), зависимости и dist, сохранив `.env`, `.telegram-worker.env`, `.local`, `.access`, `.secrets` и серверные конфигурации. Панель и Telegram worker должны использовать один выпуск.
4. Под пользователем приложения с рабочим окружением БД выполнить `npm run db:migrate`. Запустить панель и единственный Telegram worker. На панели оставить `TELEGRAM_WORKER_DISABLED=true`.
5. Проверить вход admin, выключенный деморежим, HTTPS, health, экран готовности пилота и heartbeat бота. Ошибки нельзя проверять на реальных задачах автоматическим тестовым скриптом.

## 3. Участники, роли и Telegram

Имена/связи сообщает владелец. Использовать существующие реальные профили. Для явного назначения роли есть серверный предварительный просмотр:

```bash
runuser -u ruspet -- npx tsx scripts/pilot-role.ts --user LOCAL_LEADER_ID --role sales_head
```

`LOCAL_LEADER_ID` и другие заглавные обозначения здесь — заменяемые ID, не готовые значения. `sales_head` даёт область всей компании; для ограниченной области выбирается `branch_manager` с подтверждённым филиалом. Сохранение — только после проверки с `--confirm`. Скрипт не изменяет администратора, пароли или задачи; завершает сессии изменённого пользователя. Тестовые управленческие роли нельзя оставлять реальными согласующими по умолчанию.

В «Оргструктуре» назначить непосредственных руководителей. Маршруты согласований настраиваются отдельно в правилах. Все этапы должны однозначно вести к участвующим руководителям, без самосогласования. Если согласован одноступенчатый маршрут к постановщику, его можно явно выбрать в настройках; система не меняет маршрут самостоятельно. Несколько одинаково подходящих руководителей теперь вызывают явную ошибку.

Создать персональные входы в «Настройки → Доступы сотрудников». Для каждого участника выдать его личную ссылку Telegram и попросить нажать `/start` в личном чате. Включить доставку и проверить свежий heartbeat. Приглашения действуют 15 минут и не заменяют чужую привязку. Подключать только согласованных участников; уже привязанные получатели вне пилота сохраняют ранее включённые рассылки.

Сопоставить профили с ID портала, сначала проверить имена:

```bash
runuser -u ruspet -- npx tsx scripts/bitrix-pilot.ts map-user LOCAL_PERSON_ID REMOTE_PERSON_ID
```

Если это нужный человек, повторить с `--confirm`. Идентичность проверяется через `user.get`; совпадение ФИО не используется для автоматической привязки. Нужны также постановщики пилотных задач. Существующая привязка к другому ID не заменяется.

Записать состав, сначала без сохранения:

```bash
runuser -u ruspet -- npx tsx scripts/bitrix-pilot.ts roster \
  --manager LOCAL_MANAGER_A --manager LOCAL_MANAGER_B --leader LOCAL_LEADER_ID
```

Для нескольких руководителей повторить `--leader`. После проверки повторить с `--confirm`. Роли должны быть уже назначены; эта команда не повышает права.

## 4. Выбор проекта и задач

```bash
runuser -u ruspet -- npx tsx scripts/bitrix-pilot.ts configure PROJECT_ID UF_PRICE_FIELD
runuser -u ruspet -- npx tsx scripts/bitrix.ts link LOCAL_TASK_ID REMOTE_TASK_ID
```

Проверить, что ID и портал относятся к той же задаче. При различиях команда link только сообщает поля. Явная `--accept-bitrix` разрешает создать связь с различиями; она не включает живую запись.

```bash
runuser -u ruspet -- npx tsx scripts/bitrix-pilot.ts activate LOCAL_TASK_ID
```

Активация проверяет проект, цену, участников, роли, контроль после завершения и различия. Если есть различия, она показывает список и ничего не меняет. После проверки `--accept-bitrix` подтянет подтверждённые текущие поля портала, запишет историю и начальное состояние связи. Филиал задачи сверяется с назначенным профилем исполнителя. Активные локальные согласования предварительно завершить. Повторная активация не сбрасывает очередь.

Для приёмки в Битрикс24 нужно включить контроль после завершения (`TASK_CONTROL=Y`). Иначе сдача могла бы сразу закрыть задачу; активация такого пилота блокируется. Отложенные/неподдержанные статусы сначала сверяются отдельно.

Первичная сверка сохраняет наблюдаемое состояние, не приписывая ему неизвестные прошлые переносы: счётчик переносов при начальном выравнивании не увеличивается.

`TASK_PROVIDER=mock` сохраняется как внутренняя транзакционная проекция. Не устанавливайте `real`: внешний обмен выполняет отдельная очередь этого выпуска.

Существующая выгрузка — исторический срез. Не отдавать менеджерам её как гарантированно актуальную: каждую пилотную задачу предварительно сверить с порталом. Запись не распространяется автоматически на другие 497 задач.

## 5. Проверка и включение

```bash
runuser -u ruspet -- npx tsx scripts/bitrix-pilot.ts check
```

Проверяются персональные входы, роли, подчинение, Telegram, heartbeat, проект, цена, закрытый файл вебхука, свежий ответ REST, связанные задачи каждого менеджера, постановщики и все этапы согласования. В панели администратора есть тот же экран. Локальные задачи вне обмена показываются предупреждением. Состояние резервной копии проверяется отдельно в диагностике.

В `.bitrix-worker.env` задать рабочий DATABASE_URL/пути через серверную конфигурацию при необходимости и `BITRIX_WRITE_ENABLED=true`. Файл закрытый, права `600`, не Git. Запускать проверку/enable нужно с **тем же окружением**, что и worker; `.env` читается автоматически, отдельный `.bitrix-worker.env` сам по себе CLI не подхватывает. Не выводить окружение с секретами в терминал.

```bash
runuser -u ruspet -- env BITRIX_WRITE_ENABLED=true npx tsx scripts/bitrix-pilot.ts enable --confirm
install -m 644 /opt/ruspet/ops/ruspet-bitrix-pilot.service /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now ruspet-bitrix-pilot.service
```

Служба использует `.bitrix-worker.env`. Если флаг записи хранится только там, для проверок CLI оператор должен загрузить его доверенным способом либо выставить **только** несекретный `BITRIX_WRITE_ENABLED=true` в окружении команды enable. При отсутствии любого из двух разрешений (флаг окружения и переключатель БД) запись не выполняется.

Сначала один контролируемый рабочий прогон с участниками: вход, получение своей задачи, комментарий, запрос переноса → согласование → сверка срока, сдача → приёмка/возврат → контроль статуса на портале. Проверить UI/бот от менеджера и руководителя, отсутствие чужих задач у менеджера, PDF и подтверждение напоминания. Реальные сообщения/изменения этого прогона выполняются только после настройки и в выбранных задачах, а не из тестового облачного набора.

Утренние/дневные сводки — 09:00/12:00, вечерняя — 19:01 МСК, пн–пт. При подключении после утреннего слота можно получить текущий отчёт из меню; прошлые утренние сообщения искусственно не рассылаются. Подтверждение напоминания не считается выполнением задачи.

## 6. Ошибки и остановка

```bash
runuser -u ruspet -- npx tsx scripts/bitrix-pilot.ts queue
runuser -u ruspet -- npx tsx scripts/bitrix-pilot.ts pause
```

Pause прекращает новые записи и сохраняет очередь. Уже отправленный HTTP-запрос может завершиться. Затем при необходимости остановить `ruspet-bitrix-pilot.service`; Telegram отключается отдельно, не запускать второй polling.

Для известной ошибки/конфликта сначала исправить причину и выполнить `retry EVENT_UUID --confirm`. Неизвестный результат повторять нельзя. `verify EVENT_UUID --confirm` делает контрольное чтение; для комментария требует найденный в обсуждении уникальный маркер. Если маркера нет в загруженных страницах, нужно проверить чат/старшие страницы — отсутствие в одной странице не доказывает отсутствие отправки. Прерванный обработчик также переводит начатую операцию в неопределённое состояние.

Операцию, которая уже начала передаваться в Битрикс24, нельзя автоматически отменить локальной кнопкой за 5 минут. Неотправленные операции отменяются вместе с локальным действием. Сохранённая история/отчёты не удаляются.

Для вывода отдельной задачи из пилота после паузы и завершения её очереди используйте `deactivate LOCAL_TASK_ID --confirm`. История и связь ID сохраняются.

Не восстанавливать старый дамп поверх изменений участников как обычный способ отката: сначала остановить обработчики и согласовать состояние двух систем.

Реализация сверена с официальным `bitrix-tools/b24-rest-docs`: `tasks.task.getFields`, `tasks.task.get`, `tasks.task.update`, `tasks.task.complete`, `tasks.task.approve`, `tasks.task.disapprove`, `tasks.task.renew`, REST 3.0 `tasks.task.chat.message.send`, классический `task.commentitem.add`, `user.get`. Конкретные права и особенности данного портала подтверждаются только реальным контрольным прогоном.
