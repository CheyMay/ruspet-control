# Делегирование по компании и закрытие основной задачи

## Назначение

В ОКБ у компании есть ответственный менеджер. Руководитель может выбрать его в карточке; прежние клиенты API, которые не передают `managerId`, сохраняют существующее назначение. Обычное редактирование карточки не отключает источник «Битрикс24».

Панель и бот предлагают ответственного компании из ОКБ. Если он не задан, используются точное совпадение полного имени из выгрузки ОКБ или открытые задачи компании у одного менеджера. Предложенный сотрудник должен быть в списке доступных подчинённых. При неоднозначности руководитель выбирает исполнителя вручную.

Компания определяется по связи задачи с ОКБ, единственному идентификатору `CO_<ID>` из `UF_CRM_TASK` или точному названию из поля «Компания» в выгрузке задач. Если связь с ОКБ не задана, клиента можно найти по названию или ИНН в форме делегирования. Поручение получает найденную или выбранную связь с ОКБ. Перед подтверждением проверяются версия задачи, актуальный ответственный и права. Если ответственный изменился, нужно открыть подтверждение заново.

Цена поручения — 0 ₽; бюджет, исполнитель и срок основной задачи сохраняются. Новый срок поручения не меняет срок основной задачи. Источник назначения записывается в историю.

## Приёмка

После **приёмки всех** поручений с `delegated_from_id` основная задача автоматически закрывается. В истории сохраняются ссылки на поручения и принятые результаты. Постановщик и ответственный получают уведомления. Сдача и возврат поручения оставляют основную задачу в работе. Обычные связи `parent_id` сохраняют независимые статусы.

Если у основной задачи есть активное согласование, закрытие откладывается. Обработчик панели повторяет проверку каждые 30 секунд. Блокировки цепочки защищают одновременную приёмку нескольких поручений и создание новых.

Отмена приёмки участвующего поручения возвращает автоматически закрытые задачи цепочки в работу с сохранением истории. Отмена доступна в течение 5 минут для последнего действия пользователя, если состояние задач сохранилось и передача закрытия во внешний обработчик ещё не началась.

Для активированных связей пилота приёмка из Битрикса запускает ту же проверку. Закрытие связанной основной задачи передаётся через очередь синхронизации. Первичное выравнивание старого снимка не создаёт событие новой приёмки. Поручения создаются в РУСПЭТ. Для обмена существующее поручение нужно связать и активировать по инструкции пилота.

## Синхронизация компаний

Используются документированные `crm.company.list`, `ID`, `TITLE`, `ASSIGNED_BY_ID`. Чтение идёт по возрастанию ID, страницами до 50 компаний; сохраняется весь полученный JSON, включая `UF_*`. Множественные поля CRM вроде PHONE/EMAIL маски `*`/`UF_*` не включают; для определения менеджера они не нужны. Локальные люди сопоставляются через подтверждённые `bitrix_user_links`.

Перед запуском нужен рабочий вебхук с доступом CRM, подтверждённый портал, настроенный прямой транспорт либо балансировщик и отдельная БД ОКБ. Секреты задаются файлами, как в [BITRIX-BALANCER.md](BITRIX-BALANCER.md). Поддержку REST 3.0 и внутренние повторы шлюза владелец ещё уточняет. Реальный импорт здесь не запускался.

Из каталога приложения под пользователем сервиса и с его окружением:

```bash
node --import tsx scripts/sync-bitrix-companies.ts --actor ID_АДМИНИСТРАТОРА
node --import tsx scripts/sync-bitrix-companies.ts --actor ID_АДМИНИСТРАТОРА --apply
```

Первая команда только читает портал и показывает количество/курсор без записи в ОКБ. `--apply` сохраняет. `--apply --watch` повторяет полный обход через 15 минут после предыдущего; запускать только один такой процесс. Новое назначение старой компании тоже подхватится. Службу автозапуска включать только после контрольного импорта и проверки сопоставлений.

По умолчанию максимум 100 страниц, настраивается `--max-pages` (1–1000). При достижении лимита программа сообщает `complete:false`, курсор `after` и завершает работу с ошибкой; продолжение разового импорта — `--after <курсор>`. Периодический режим требует полного обхода с нуля. Повторный импорт идемпотентен; ошибка не вызывает удаления уже загруженных компаний.

Идентичность — портал + ID Битрикса. Автоматического объединения с существующими ручными карточками по названию/ИНН нет. При необходимости существующим карточкам следует отдельно подтвердить внешнюю связь до импорта. Новый импортированный клиент получает бизнес-статус «Не указан», а не вымышленный этап продаж. При повторе сохраняются статус, ИНН, контакт и заметки; название и ответственный обновляются из портала. Ручная смена менеджера импортированной компании действует до следующей синхронизации. Удаление/передача компании вне прав вебхука не определяется автоматически: ранее загруженная карточка остаётся в ОКБ.

## API для будущих интеграций

Все методы требуют действующую сессию и общие проверки доступа/источника запроса. Публичного входящего вебхука нет.

- `GET /api/okb/companies/:id/responsibility` — версия компании, локальный ответственный, источник, внешний ID ответственного и время синхронизации; доступ руководству.
- `POST /api/okb/companies`, `PUT /api/okb/companies/:id` — существующие методы карточки с необязательным `managerId` (ID сотрудника или null); PUT требует текущий `version`.
- `POST /api/integrations/v1/companies/batch` — только администратор; JSON `{portal,dryRun,companies:[{externalId,name,externalManagerId,raw}]}`. `dryRun` по умолчанию true; до 50 разных компаний, до 512 КиБ. Нормализованные поля должны совпадать с исходным снимком. Портал должен совпадать с настроенной интеграцией. В ответе — план/результат без сырых полей.
- `GET /api/tasks/:id/delegation-targets` — разрешённые сотрудники + рекомендация `responsibility` с токеном версии назначения.
- `POST /api/tasks/:id/delegate` — `expectedVersion`, для автоматического выбора — `responsibilityToken` без `assigneeId`; для ручного — `assigneeId`. Прежние ручные клиенты совместимы.

Для автономного внешнего клиента в будущем понадобится отдельная серверная аутентификация; сессионные API нельзя выдавать за готовый публичный интеграционный шлюз.

## Обновление

Панели и боту нужен одинаковый код выпуска и свежий `dist/`. После обычной резервной копии, установки зависимостей и до запуска нового кода выполните **обе** миграции с серверным окружением:

```bash
node --import tsx scripts/migrate.ts
node --import tsx scripts/migrate-okb.ts
npm run check
npm run build
```

Первая применяет основные миграции до `020_company_delegation.sql`; вторая повторно обновляет отдельную схему ОКБ (идемпотентно). Не подставлять основную БД в `OKB_DATABASE_URL`. Если ОКБ ещё не заведена, сначала настроить отдельную БД; без неё делегирование работает через ручной выбор. Перезапуск конкретных служб и копирование кода выполняются по существующей схеме сервера; эта инструкция сама по себе ничего не развёртывает.

Для известной установки `/root/ruspet-code` → `/opt/ruspet` подготовлен `scripts/update-server.sh` (root). Он проверяет имена БД и каталог служб, блокирует одновременное обновление, получает ветку `feature/company-delegation`, строит интерфейс с ограничением CPU 60%, останавливает только действующие панель/локальный worker, сохраняет дампы/код/настройки и прежние зависимости, копирует код и dist в рабочий каталог, выполняет обе миграции (ОКБ только если настроена), выключает обмен Битрикс24 и возвращает ранее работавшие службы. В конце сравнивает реально отдаваемые index.html и theme-init.js с новой сборкой. Секреты и `.local` сохраняются, импорт задач не запускается. Скрипт запускать из копии вне Git-каталога. На VPS из текущей среды не выполнялся: SSH/DNS и настроенный TCP-прокси недоступны; проверен синтаксис Bash. При ошибке после остановки службы автоматически не запускаются — требуется проверить причину, резервная папка выводится в консоль.
