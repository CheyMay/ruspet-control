# Обновление задач и напоминаний

Ветка `feature/task-reminders` включает тёмную тему и требует **полного обновления панели и отдельного Telegram worker**. Прежние команды, копирующие только `dist/`, для этого выпуска не подходят. Доступ к VPS из облачной задачи не настроен; развёртывание и реальные отправки здесь не выполнялись.

## Что меняется

- Редактирование активной задачи: только постановщик либо руководитель в текущей области доступа. Исполнитель может сдавать работу и предлагать срок, но не редактировать чужую постановку. Название, описание, исполнитель и причина изменения доступны в боте; крайний срок — исключительно через существующий маршрут согласования. Версии и повторные подтверждения защищены транзакциями. Сдача, приёмка, возврат, согласование и отказ требуют пояснения (не меньше 5 символов; причина/план переноса — по настройке правил).
- Качество: фильтры по себе, своим постановкам, доступной команде, исполнителю, постановщику, правилу, серьёзности, трём и более нарушениям, просрочке больше недели. Сотрудник видит в качестве только задачи, где он исполнитель. Пользовательская иерархия подчинения ещё не реализована: действуют текущие роли/филиалы и серверная область доступа.
- Первоначальный срок удалён из карточки: это не дата создания. Значения в БД и исходной выгрузке сохранены. «Показывать планирование» выключено по умолчанию; включает плановые даты, нагрузку и проверки планирования. При выключении план следующего дня не создаётся по расписанию и скрыт в архивной выдаче; старые отчёты не удаляются. При редактировании со скрытым планированием существующие даты сохраняются. Путь рабочего дня на главной сохранён.
- Письменные правила: точные шаблоны из настроек (буквенный код, обязательный крайний срок, минимум символов описания). Регистр/пробелы нормализуются; количество символов можно менять. Свободный русский текст, составные условия и произвольные бизнес-правила пока не интерпретируются. Неподдерживаемые формулировки отклоняются. После изменения правил запустите проверку, чтобы обновить сохранённые нарушения.
- Личные напоминания: дни, до 8 различных времён в день, 1–52 недели. В панели — квадратики дней, переключатель нескольких времён и числа недель; в боте — дни кнопками, затем время и недели. Расписание можно выключить; новое не изменяет историю старого. Получатель подтверждает «ОК, увидел» в боте или панели; это не завершение задачи. Без подтверждения — повтор через 30 минут после последней попытки до конца московского дня. Одинаковое расписание, повторно сохранённое в тот же день, не дублируется.
- Будни: собственные просрочки и задачи на сегодня после 09:00 МСК, повторная оценка оставшихся просрочек после 12:00 (включая истёкшее время сегодняшних задач). Утреннее сообщение действует до 12:00, дневное — до конца дня. Пропущенные прошлые дни не рассылаются; поздний запуск показывает фактическое время расчёта. Праздничный календарь не настроен.
- Доставка только в привязанные личные чаты при включённых `telegram_settings.enabled` и `delivery`, независимо от расписания отчётов. Подтверждение Telegram, подтверждение человеком и неизвестный исход отправки различаются. После неизвестного исхода автоповтор конкретного сообщения остановлен, чтобы не дублировать возможную отправку; напоминание доступно в панели/меню бота. При явно отклонённой отправке следующая попытка — не раньше 30 минут. Завершённые/недоступные задачи не доставляются.
- Каждому пользователю соответствует отдельный чат. Существующая привязка сохраняется; другая ссылка не заменяет ни пользователя чата, ни его чат. Пользователь может привязать себя; администратор может создать одноразовую ссылку на 15 минут для выбранного сотрудника (в том числе пока без веб-логина). Ссылку нужно передавать лично этому сотруднику. Чужим/групповым чатам бот не отвечает. На панели без Telegram-токена ссылки используют имя бота, сохранённое работающим worker в БД.

## Порядок развёртывания

1. На обеих машинах зафиксировать текущую версию и сохранить защищённые резервные копии кода/конфигурации. На российском сервере сделать свежий `pg_dump` рабочей БД `ruspet_demo` (в файл с правами 600, не в чат/терминал/Git). Рабочую БД не заменять исходной выгрузкой; `db:seed` не запускать.
2. В отдельной Git-копии получить `origin/feature/task-reminders`, проверить отсутствие локальных правок, выполнить последовательно `npm ci`, `npm run check`, `npm run build`. Использовать Node.js >=22.12 и ограниченную параллельность, например `GOMAXPROCS=1 npm run build`. Получать конкретный проверенный коммит; не смешивать файлы разных веток.
3. Остановить только `ruspet-bot` на зарубежном сервере. Не запускать вторую копию polling; SSH-туннель `ruspet-db-tunnel` оставить работающим.
4. Обновить код панели `/opt/ruspet` из проверенной Git-копии: `server/`, `shared/`, `scripts/`, `web/`, манифесты и сборку. Сохранить серверные `.env*`, `.viewer.env*`, `.local/`, `.access/`, секреты, runtime-настройки и служебные файлы. Не превращать каталог работающего приложения в Git через принудительный reset/checkout. Сохранить владельца `ruspet` и доступ службы к файлам.
5. Выполнить `npm run db:migrate` из `/opt/ruspet` под пользователем приложения **с тем же локальным DATABASE_URL и окружением, что у ruspet.service**. Точный способ передачи окружения зависит от настроенной службы; не печатать `systemctl show Environment`, `.env` или строку подключения. Нужна миграция `008_reminders.sql` на общей БД. Она добавляет таблицы расписаний/подтверждений/очереди и расширяет существующую привязку чатов; задачи и пароли не перезаписывает.
6. Перезапустить `ruspet.service`. Проверить локальный `/api/health` (200), `/api/bootstrap` без сессии (401), `/api/demo/users` при production-настройках (403), HTTPS сайта и входы. Для двух существующих входов есть `scripts/verify-production-login.ts`: файл доступов передавать только локальным путём на VPS, не публиковать его содержимое.
7. Обновить зарубежный `/opt/ruspet-bot` до того же коммита (серверные модули, shared, scripts, манифесты/зависимости), сохранив секреты и настройки туннеля. Перезапустить единственный `ruspet-bot`. На российском веб-процессе оставить `TELEGRAM_WORKER_DISABLED=true`.
8. Проверить heartbeat и ошибки в «Рабочем боте», затем под администратором создать нужные привязки. Отправки возможны только после личного `/start` получателя. Доставка новых событий должна быть включена. Проверку реального сообщения и подтверждения выполняет владелец/подключённый получатель; в разработке сетевые ответы Telegram подменялись.

Для отката использовать сохранённый комплект кода/сборки и прежние службы. Новые таблицы и историю подтверждений не удалять; не восстанавливать старый дамп поверх уже сделанных пользователями изменений без отдельного решения.

## Битрикс24: граница реализации

Настоящий Bitrix-адаптер пока отсутствует. Изменение задачи, запись истории и операция `task_sync_queue` сохраняются одной транзакцией. Очередь хранит снимок, версию, причину/комментарий и ключ операции. `processTaskSync` обрабатывает версии в порядке, по одной операции в секунду, с задержкой повторов; тесты используют подставной адаптер. Ошибка старой версии блокирует отправку следующих версий той же задачи.

В production этот обработчик **не подключён к сети**, провайдер остаётся `mock`; статус `/api/task-sync` явно сообщает `connected=false`. Для реального обмена необходимы документированное сопоставление полей/ID, учётные данные и права, сверка внешних версий и обработка идемпотентности/неопределённого результата. Названия функций в коде не являются выдуманными Bitrix REST-методами. Не включать отправку накопившейся mock-очереди без отдельной сверки с реальными задачами.
