## Рабочий бот и очередь действий · 2 ноября 2026

Проверка текущего запуска: TypeScript, сборка и 28 тестов прошли. В рабочей базе осталось 497 исходных задач; сценарные тесты выполнялись отдельно. Реальный Telegram ответил, проверен бот `@b_ruspet_bot`; включён личный пилот с доставкой новых событий, ожидается привязка единственного чата. Первый сетевой запрос оборвался, повторное подключение прошло успешно; состояние соединения показывается в панели. Одноразовые ссылки не сохраняются в документации, новую можно получить в разделе «Рабочий бот» под администратором.

Новый этап добавляет разделы «Нужно действие» и «Рабочий бот». Последний содержит рабочий предпросмотр под выбранной ролью и настройки личного Telegram-пилота. Предпросмотр выполняет настоящие локальные действия, он не создаёт отдельную копию базы.

- В боте: меню, очередь, задачи с постраничным просмотром, поиск /task НОМЕР, карточка, полная история частями, архив сводок, структурированный ответ, предложение срока, решения по маршруту, сдача результата, возврат и повторная сдача. Текст и ссылки; загрузка файлов пока не реализована.
- Черновики хранятся час, ответы вводятся по шагам. Перед отправкой есть подтверждение и отмена. Переход в меню или другую карточку отменяет незавершённый ввод.
- Каждая сдача имеет номер, автора, результат и отдельное решение. Содержимое прошлой сдачи изменить нельзя. Для задач, импортированных уже на приёмке, неизвестная история не восстанавливается искусственно.
- Действие и подтверждение обработки кнопки записываются одной транзакцией. Двойное нажатие возвращает сохранённый результат, старый этап не согласует следующий. Права проверяются повторно при применении.
- Реальные вызовы Telegram вынесены в server/telegram-pilot.ts. Личный пилот выключен по умолчанию. Его включает администратор в «Рабочем боте», затем получает одноразовую ссылку на 15 минут и нажимает «Начать» в Telegram. Допускается один личный чат, новый чат не заменяет уже привязанный. Никому вне привязки ответы не отправляются.
- Доставка новых уведомлений включается отдельно. Отправляются только записи, адресованные привязанной учётной записи и созданные после включения/привязки, пакетами до 12 событий. Старая очередь не рассылается. «Отправлено» означает подтверждение Telegram, а не прочтение человеком. Неопределённый исход отправки виден отдельно и автоматически не повторяется.
- Старый server/telegram.ts — неиспользуемый прототип. Bitrix-провайдер остаётся mock. Личный чат привязывается к администратору; другие роли проверяются через предпросмотр или панель. Массовое подключение сотрудников и серверное размещение пока не включены.
- Основной экран сдачи использует существующие права постановщика/руководителя на приёмку. Старый отдельный API маршрутного закрытия сохранён для совместимости; обычному сотруднику в карточке предлагается единая кнопка сдачи. Финальные маршруты компании требуют назначения реальных руководителей.

При реализации транспорта сверены официальные [кнопки Telegram](https://core.telegram.org/bots/api#inlinekeyboardbutton), [getUpdates](https://core.telegram.org/bots/api#getupdates) и [подтверждение кнопок](https://core.telegram.org/bots/api#answercallbackquery).

Ниже — описание предыдущих этапов; утверждения об отключённом Telegram относятся к версии до личного пилота.

# РУСПЭТ — контроль и согласование задач

Рабочий локальный MVP: React + TypeScript, Node.js/Express + TypeScript, PostgreSQL. Битрикс24 и Telegram отключены, внешних запросов к ним нет. Работа идёт с локальной копией реальных данных Excel; звонков нет.

## Запуск

Нужен Node.js 22.12+ (на текущем компьютере используется 24). Из папки проекта:

```powershell
npm ci
npm run build
npm run dev
```

Открыть **http://127.0.0.1:4310**. Первый запуск создаёт локальную PostgreSQL на порту 55439, применяет миграции и импортирует данные. Следующие запуски сохраняют изменения. Остановка — Ctrl+C. Данные и случайный пароль локальной БД находятся в `.local/`, эта папка исключена из Git. `npm run dev` обслуживает собранный интерфейс; после изменения React/CSS повторите `npm run build`. API после изменения кода нужно перезапустить.

Для собственной PostgreSQL задайте `DATABASE_URL` в `.env`, затем выполните `npm run db:migrate`, `npm run db:seed`, `npm start`. Импорт разрешён только в пустую БД; повтор того же исходного файла ничего не перезаписывает.

## Данные

- Источник: **руспет.xlsx**, первый лист **Лист1**, 497 уникальных задач, 38 столбцов, 8 исполнителей. 17 уникальных людей встречаются среди исполнителей и постановщиков.
- `data/first-sheet.json` — сохранённые значения первого листа. Исходная книга не изменялась. Все столбцы доступны в карточке → «Исходные поля выгрузки». В БД также сохраняются номер строки и хеш импорта.
- 494 «Ждёт выполнения» и 1 «Выполняется» отображаются в общей категории «В работе»; 2 «Ждёт контроля» — «На приёмке». Исходный статус сохранён отдельно.
- Время без часового пояса интерпретировано как Москва (UTC+3). Сроки не сдвигались на будущие даты. Просрочка считается относительно текущего времени, поэтому это состояние по исторической выгрузке, а не актуальное состояние Битрикс24.
- Филиалы, первоначальные сроки и предшествующая история переносов в файле отсутствуют. Филиал обозначен «Не указан», исходный срок — неизвестен, счётчик считает только новые изменения после импорта. Приоритет не выводится из несвязанных полей.
- Реальным людям не приписаны должности руководителей. Для демонстрации маршрутов добавлены четыре явно тестовые учётные записи: администратор, директор, руководитель филиала, руководитель продаж. Настоящие роли и филиалы требуют отдельного назначения.
- Поддельные комментарии, согласования, отчётные снимки и выполненные проверки к импортированным задачам не добавлялись. Они появляются только после действий пользователя.
- Проект содержит реальные данные компании. Не публикуйте исходники с `data/first-sheet.json` и `.local/` без отдельного решения.

## Что можно пройти самостоятельно

1. В «Задачах» найти номер или сотрудника, открыть карточку, сверить исходные поля. Таблица показывает по 50 строк.
2. Под тестовым директором запустить проверку. Открыть нарушения и журнал mock-уведомлений.
3. Выбрать исполнителя задачи в верхнем переключателе. В карточке → «Обсуждение» дать структурированное объяснение.
4. Запросить перенос на будущую дату с причиной и планом. Срок до решения не изменяется.
5. Выбрать тестового руководителя филиала и согласовать первый этап; затем тестового руководителя продаж и согласовать второй. Проверить срок, историю и счётчик переносов.
6. Для закрытия маршрут: тестовый руководитель филиала → тестовый директор. «Отказать» останавливает запрос; «Вернусь позже» не меняет задачу.
7. Под администратором в карточке можно имитировать изменение описания в источнике. Активный запрос станет устаревшим; повторное согласование не применится.
8. Создать локальную задачу. Исполнитель сдаёт результат, постановщик/руководитель возвращает с замечаниями или принимает. Свою работу принимать нельзя; все переходы видны в истории.
9. В «Отчётах» сохранить снимок и скачать CSV. Каждое новое нажатие создаёт новый снимок. Повтор сетевого запроса с тем же requestId возвращает уже сохранённый результат.

## Ограничения и следующий этап

- Переключение пользователей — **демонстрационный вход**, не производственная авторизация. Сервер намеренно слушает только loopback; не размещать его за публичным прокси до добавления нормального входа.
- Реальные Битрикс24 и Telegram отключены. Сохранённый экспериментальный модуль Telegram не импортируется при запуске, привязка отключена на API. Наличие токена в локальном хранилище не запускает бот.
- Порт провайдера в `server/providers.ts` — внутренний контракт приложения, а не перечень методов Bitrix24. Real REST/event-адаптер пока не написан; его включение вызывает ошибку. Для него нужны проверенные официальные контракты, отдельный обработчик очереди, сверка версий, повторы и обработка неоднозначного результата внешней записи. Локальная транзакция mock не обещает атомарность внешнего API.
- Проверки и отчёты доступны вручную и по включаемому расписанию. Нет производственного календаря, отпусков, заместителей, пакетирования сообщений и автоматических реальных рассылок.
- Формальная длина ответа не означает смысловую проверку. Проверка буквенных кодов сверена с GAS и по умолчанию выключена. Проверки плановых дат, длительности до 6 часов и сроков родителя доступны отдельным переключателем. Если родитель/дети отсутствуют в доступной выборке, показывается справочное сообщение. Исходные KPI GAS не перенесены: нет подтверждённой формулы и истории закрытых задач.
- Есть снимки по очередям и итоги по событиям после импорта. Автоматические утренние/вечерние снимки имеют отдельные ключи и не подменяются ранним ручным отчётом. Есть CSV для Excel, печатная HTML-версия для сохранения в PDF средствами браузера и сравнение соседних снимков. Нативный XLSX, исторические KPI и произвольные периодные показатели пока не реализованы.
- Импорт — безопасная первоначальная загрузка; повторная сверка изменившегося Excel с рабочими задачами пока не реализована.
- Масштаб текущего среза: одна компания, небольшой набор данных. Отдельные тенанты, серверная пагинация и промышленное развёртывание не реализованы.

## Текущая версия · 1 ноября 2026

- Шесть очередей складываются в общее количество: просрочены до сегодня + срок сегодня + срок впереди + без срока + приёмка + завершённые. Приёмка не смешивается с активными просрочками. Истёкшее сегодня время отмечается внутри сегодняшней очереди.
- Согласования, ожидание объяснения и риск клиента — пересекающиеся признаки, отдельно от этого равенства. Каждый показатель открывает соответствующие задачи. Дашборд и список используют одну функцию классификации.
- Нагрузка — сумма частей плановых интервалов в каждом московском дне. Это календарные часы, не фактическая занятость или эффективность. Данные с неполным планом обозначены отдельно.
- Шесть видов отчётов: snapshot, today, overdue, review, daily, nextday. План следующего рабочего дня пересекает плановые интервалы, исключает приёмку и завершённые; календарь пн–пт без праздников. Архив ищет по всему сроку хранения, фильтруется по виду и диапазону дат, показывает по 20 записей на страницу.
- GET /api/reports/:id — сохранённый состав; /csv — экспорт с русскими статусами и московским временем. CSV защищён от формул, начинающихся с =, +, -, @.
- POST /api/tasks, PUT /api/tasks/:id, POST /api/tasks/:id/review — локальное создание, редактирование и сдача/приёмка/возврат. Редактирование не позволяет обходить согласование крайнего срока. Изменение версии делает старый маршрут неактуальным.
- История хранит автора, время, причину, результат, замечания и пары значений до/после. Это основа для будущей такой же истории в Telegram; кнопки и доставка через Telegram сейчас отсутствуют.
- На 1 ноября пройдены TypeScript, сборка и 18 автоматических проверок в отдельной БД. Ручная проверка интерфейса и бизнес-формулировок остаётся пользователю.

Исходный HTML-референс недоступен, поэтому точное совпадение с ним не заявляется. Это локальный MVP для совместной проверки процессов; производственный вход, реальные назначения руководителей, резервное копирование и восстановление на сервере нужны до эксплуатации компанией.

## Обновление задач и напоминаний

Новые возможности, ограничения письменных правил и Bitrix, привязка личных чатов и порядок миграции/обновления обоих серверов описаны в [UPGRADE-REMINDERS.md](UPGRADE-REMINDERS.md). Старые утверждения об одном тестовом чате и приёмке без комментария относятся к предыдущей версии.

### Диагностика и резервные копии

В «Настройках» администратора есть состояние Telegram, очередь доступных к доставке событий и напоминаний, последние результаты отчётов, а также доступы сотрудников. Приглашение в Telegram создаётся на 15 минут и передаётся сотруднику вручную. Роли и веб-аккаунты по-прежнему задаются отдельно.

На Linux-сервере администратор устанавливает расписание командой `sudo bash scripts/install-backups.sh` из доверенной копии репозитория. База по умолчанию называется `ruspet_demo`. Для другого имени задайте `RUSPET_BACKUP_DB` в окружении обоих systemd-сервисов через drop-in. Копии хранятся в `/var/backups/ruspet`. Сохраняются 14 последних и дополнительно последняя проверенная, если она старше. Это локальные копии на том же сервере.

- Копия каждый день в 03:30 МСК, пробное восстановление по воскресеньям в 04:15 МСК.
- Для немедленной проверки запустите по очереди `sudo systemctl start ruspet-db-backup.service` и `sudo systemctl start ruspet-db-restore.service`. Вторая команда проверяет контрольную сумму и восстанавливает архив во временную базу. Затем сверяет доступность основных таблиц, считает строки и удаляет временную базу.
- Панель показывает результат и время последней попытки. Подробности доступны в `journalctl -u ruspet-db-backup.service -u ruspet-db-restore.service`.
- Медиана и P95 считаются по реальным ответам бота за последние семь дней. Отдельно можно проверить время подготовки на сервере командой `npx tsx scripts/benchmark-bot.ts`. Она готовит меню, карточку и PDF существующего отчёта, удаляет свои временные кнопки и не отправляет сообщения.

### Пилот Битрикс24

Пилот запускается отдельной командой из каталога приложения. Панель и бот читают PostgreSQL. Укажите `BITRIX_PORTAL` (домен без схемы) и `BITRIX_WEBHOOK_FILE` (закрытый файл с HTTPS-адресом входящего вебхука). Для тестового пользователя нужны права на выбранный проект, задачи и их чаты. Не помещайте URL вебхука в команды, Git или логи.

1. `npx tsx scripts/bitrix.ts scan <ID проекта> 0 10` читает максимум десять страниц в буфер. Следующий проход продолжайте с показанного `cursor`. Буфер отделён от рабочих задач. Для задач из Excel сопоставляйте ID на том же портале, а новые задачи рассматривайте отдельно.
2. `npx tsx scripts/bitrix.ts link <ID РУСПЭТ> <ID Битрикс24>` сверяет название, описание и срок. При расхождении выводит список полей. Для подтверждённой пары параметр `--accept-bitrix` разрешает привязку с различиями. Следующий `sync` подтянет поля Битрикс24 в локальную задачу.
3. `npx tsx scripts/bitrix.ts activity <ID РУСПЭТ>` сохраняет доступные комментарии и историю. Для предыдущей страницы новой карточки передайте показанный `olderThan` следующим аргументом. В старой карточке используйте `BITRIX_LEGACY_COMMENTS=true` только после проверки формата портала. Данные видны администратору в карточке. Вложения, удалённые сообщения и исторические версии текста пока отдельно не синхронизируются.
4. `npx tsx scripts/bitrix.ts sync <ID РУСПЭТ>` делает сверку одной пары и применяет разрешённые входящие поля. После проверки пилота запись включается сочетанием `BITRIX_WRITE_ENABLED=true` и `--write`. При споре по одному полю автоматическое применение блокируется. После записи выполняется контрольное чтение. Снятие срока, статусы, исполнители, создание задач и отправка комментариев в Битрикс24 находятся за пределами пилота.
5. `BITRIX_POLL_ENABLED=true npx tsx scripts/bitrix.ts watch` опрашивает только связанные задачи, начиная с давно не проверявшихся. Для опроса обсуждений дополнительно включите `BITRIX_ACTIVITY_ENABLED=true`. Перед ручной командой остановите экземпляр `watch`, так как он удерживает блокировку пилота. Массовое подключение должно использовать события как сигнал для сверки, а опрос оставаться подстраховкой.

Один запрос за раз с минимальным интервалом 1,1 секунды. Лимитер общий для процессов на этой базе, с паузой после ошибок интенсивности и ресурсоёмкости. Другие интеграции с того же исходящего IP делят бюджет портала. Битрикс24 не предоставляет условную запись в используемом методе, поэтому перед массовым включением нужно проверить сценарий одновременной правки на портале.

Официальные источники: [лимиты](https://apidocs.bitrix24.ru/settings/performance/limits.html), [новая карточка задач](https://apidocs.bitrix24.ru/api-reference/tasks/tasks-new.html), [чтение списка задач](https://apidocs.bitrix24.ru/api-reference/tasks/tasks-task-list.html), [запись полей](https://apidocs.bitrix24.ru/api-reference/tasks/tasks-task-update.html).

### Расписания, процессы и ОКБ

В «Задачи → Создать задачу» можно выбрать разовую задачу, расписание или условие из ОКБ. Дополнительные поля содержат произвольные подписи и текстовые значения. Расписание задаёт первый запуск по МСК, интервал в днях, неделях или месяцах и относительный срок. Для месячного расписания на 31-е число в коротком месяце берётся последний день. После простоя создаётся одна ближайшая пропущенная задача, затем расписание продолжается.

«Бизнес-процессы» поддерживают первое семейство сценариев Draw Run: создание компании или смена статуса, одно условие, ветки «Да» и «Нет», задача в выбранной ветке. Черновик можно проверить без создания задачи и включить явно. Включение учитывает новые события. Для редактирования сначала остановите процесс. Выбранная ветка, созданная задача и ошибки видны в журнале. Панель обрабатывает расписания и события примерно раз в 30 секунд.

ОКБ хранится в отдельной базе PostgreSQL. Реестр доступен администратору, директору и руководителю продаж. В локальном режиме с встроенным PostgreSQL `npm run dev` создаёт базу `ruspet_okb` автоматически. При внешнем PostgreSQL создайте отдельную пустую БД, задайте `OKB_DATABASE_URL` и примените `npx tsx scripts/migrate-okb.ts`. На Linux для базы `ruspet_okb` используйте `sudo bash scripts/install-backups.sh okb` из доверенной копии. Копия ОКБ создаётся в 03:45 МСК, пробное восстановление по воскресеньям в 04:30 МСК. При аварийном восстановлении обе базы нужно рассматривать вместе, так как журнал и позиция обработки событий ОКБ находятся в основной базе.

### Постановка задач и история компании

Форма задачи поддерживает быстрые сроки, личные шаблоны и общие шаблоны руководителей. Шаблон заполняет пустые поля и добавляет недостающие дополнительные поля. Компания, исполнитель и даты в шаблон не сохраняются. Подсказки используют только доступную пользователю выборку задач.

Из карточки компании можно создать связанную задачу, открыть задачи и их историю или зафиксировать контакт. Для активной компании событие «Давно не было контакта» возникает один раз за период тишины. Отсчёт идёт от последнего записанного контакта или от добавления компании. Процессы реагируют на новые события после включения. Событие приёмки ждёт окончания окна отмены. Принятие задачи, созданной самим бизнес-процессом, не запускает цепочку повторно. Рабочие правила включаются вручную.

### Делегирование

Руководитель может делегировать свою задачу в работе из карточки или Telegram. Панель даёт уточнить поручение и крайний срок, Telegram использует срок исходной задачи. Поручение связано с исходной задачей, имеет цену 0 ₽ и возвращается делегировавшему на приёмку. Одновременно одному сотруднику можно выдать одно открытое поручение из одной исходной задачи. Руководитель филиала выбирает сотрудников своего указанного филиала, руководитель продаж — руководителей филиалов и сотрудников, директор и администратор — подчинённые операционные роли по компании.

### Оргструктура, поручения и версии процессов

В «Оргструктуре» администратор и директор могут указать прямого руководителя и назначить временное замещение в пределах действующей области доступа. При делегировании явные связи имеют приоритет. Пока у руководителя нет настроенных подчинённых, применяется прежняя выборка для сотрудников без явно назначенного руководителя. Замещение действует на делегирование и очередь «Мои поручения» в заданные даты. Маршруты согласований настраиваются отдельно.

В «Моих поручениях» видны выданные задачи, связанные исходные задачи при наличии доступа, сроки и приёмка. Очередь включает доступные поручения руководителей, которых пользователь сейчас замещает.

Новые процессы строятся как граф Draw Run. Старт, условия, задачи и финиш соединяются именованными выходами. Схема проверяется перед предпросмотром и публикацией. Пробный запуск показывает путь и задачи без записи рабочих данных. Черновик хранится отдельно от опубликованной версии. Публикация выполняется вручную и применяется к новым событиям. Журнал показывает версию, маршрут и созданные задачи. Существующие линейные процессы продолжают выполняться и могут быть перенесены на доску через редактор.

### Показатели в бизнес-процессах

Выберите событие «Проверка показателей по расписанию», сотрудника или всех менеджеров по отдельности и интервал проверки. Блок «Показатель по задачам» считает количество, сумму цен или сумму переносов по задачам рабочей выборки. Фильтры одного блока применяются вместе. Ветвление и несколько блоков позволяют собрать более сложные условия. Категории цен совпадают с панелью. Периоды крайнего срока используют московский календарь, дни просрочки считаются как фактическое время после срока.

На выходе можно создать задачу или поставить уведомление в общую очередь Telegram. Получателя можно указать прямо или выбрать прямого руководителя из оргструктуры. Для проверки по расписанию получателю нужен доступ к задачам выборки. Доставка использует действующую привязку Telegram и настройки доставки. Текст может включать `{{subject.name}}` и `{{metric.value}}`. Пробный запуск считает на текущих данных без постановки задач или уведомлений. Повторный обход сохраняющегося условия не создаёт дублей. После выхода из условия действие снова доступно при новом срабатывании.

Для выпуска доступны фильтры по задачам, включая дополнительные поля по имени. Справочник находится в `shared/process-metrics.ts`. Новые показатели и наборы данных добавляются через типизированные источники и проверку прав.
