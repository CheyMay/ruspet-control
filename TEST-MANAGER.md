# Тестовый менеджер на старом VPS

Владелец попросил показать работу менеджера на старом сервере, исключив Шевченко и Чекальского. По умолчанию подготовлен **отдельный учебный контур**: база `ruspet_manager_preview`, Linux/PG-пользователь `ruspetpreview`, роль в приложении employee, вход `test.manager`, 24 вымышленные задачи для четырёх менеджеров. Вход выбирает одного подходящего менеджера с активными задачами; фиксированные имена, выбранные участники пилота, отключённые аккаунты и люди с действующими связями задач Битрикса исключаются.

Рабочие пользователи, пароли, 497 задач и основной бот не меняются. Копируется **код** действующего приложения, а не рабочая БД. Схема и seed учебных данных запускаются только после проверки точного имени тестовой БД и отдельной PG-роли. Бот проверяется через встроенный экран в веб-интерфейсе; реальный Telegram/QR этого контура выключен. Основной Telegram-бот продолжает работать с рабочей БД. Для отдельного живого Telegram-теста нужен отдельный тестовый бот либо явно согласованный тест в рабочей системе.

## Просмотр панели от имени сотрудника

Войдите администратором, откройте «Настройки» → «Доступы сотрудников», найдите нужного человека и нажмите «Открыть как сотрудник». В отдельной вкладке появятся задачи, согласования, действия, уведомления, отчёты и другие рабочие данные, доступные этому человеку. Для просмотра персональный логин сотрудника не требуется. Изменения и административные запросы в этом режиме блокирует API. Основная вкладка остаётся в вашей сессии.

На учебном стенде `preview.admin` нужен для просмотра, `test.manager` — для реальных действий на учебных задачах и работы во встроенном боте. Если оба входа открыты одновременно, используйте разные профили браузера. Установка из подготовленного выпуска поддерживает флаги `--source` и `--passwords-stdin`: первый принимает закрытый staging-каталог в `/root`, второй читает по одной строке для менеджера и учебного администратора.

## Установка владельцем

Выполнять на **старом VPS** `9181f0e55d8.vps.myjino.ru`, SSH 49352, из root-консоли. Агент из облачной среды напрямую не подключён и не создавал аккаунт в рабочей БД. Сначала забрать только новые самостоятельные вспомогательные файлы; рабочую ветку и файлы приложения не переключать:

```bash
bash <<'SH'
set -euo pipefail
cd /root/ruspet-code
GIT_SSH_COMMAND='ssh -i /root/.ssh/ruspet_github -o IdentitiesOnly=yes' \
 git fetch origin feature/test-manager-access
for file in server/test-manager-access.ts scripts/setup-manager-preview.ts scripts/manager-preview-server.ts scripts/install-manager-preview.sh; do
 git show "FETCH_HEAD:$file" > "/opt/ruspet/$file"
 chmod 0644 "/opt/ruspet/$file"
done
systemd-run --scope --quiet -p CPUQuota=60% nice -n 10 \
 env GOMAXPROCS=1 bash /opt/ruspet/scripts/install-manager-preview.sh
SH
```

В установщике дважды ввести собственный пароль для test.manager (12–200 символов). Ввод скрыт; пароль не передаётся через аргументы/env/чат и не выводится. Он передаётся программе хеширования через stdin и хранится только как scrypt. Тестовый менеджер и количество его задач будут показаны после настройки.

Проверки до записи: root, действующая служба РУСПЭТ на старом сервере, свободный loopback 4320, не менее 384 МБ доступной RAM, место под копию кода плюс запас 1 ГБ, отсутствие прежнего стенда/БД/служебного пользователя. Общий lock не даёт пересечься с обновлением. Установщик не перезаписывает прежний стенд, не сбрасывает чьи-либо пароли и не останавливает рабочие службы. При частичной ошибке не удалять рабочие данные: сначала проверить этап, отдельно очистить только собственный незавершённый тестовый контур.

Сервис `ruspet-manager-preview.service` использует отдельную копию server/shared/scripts/dist/node_modules в `/opt/ruspet-manager-preview`, свой .env и БД. Секреты, .env, .local и реальные data/ из `/opt/ruspet` не копируются. PG-роль без прав суперпользователя/создания БД; служба не имеет доступа к `/opt/ruspet`, /root и записи в код. CPUQuota=35%, MemoryMax=384M. Входная точка запускает только HTTP, без polling/планировщиков/фонового обмена. Включён обычный парольный вход, демонстрационное переключение ролей выключено. Обновления основного сайта не заменяют копию кода стенда автоматически.

## Открыть сайт

В PuTTY **соединения со старым сервером**: Connection → SSH → Tunnels:

- Source port: `4320`.
- Destination: `127.0.0.1:4320`.
- Local → Add → Apply.

Держать SSH-соединение открытым. В браузере открыть `http://127.0.0.1:4320`, логин `test.manager`, пароль тот, который ввели. Публичный порт, домен и HTTPS для этого не требуются: трафик идёт через SSH-туннель. Это отдельный сайт с учебными данными, не cheymay.ru и не новый корпоративный VPS. Если браузер параллельно работает с другим сайтом на 127.0.0.1, использовать отдельный профиль/инкогнито, чтобы cookie приложений не конфликтовали.

Можно посмотреть задачи/фильтры, оставить комментарий, запросить перенос, сдать задачу и проверить встроенный бот. Согласования пойдут учебным руководителям этой базы; никаких реальных сообщений им не отправляется. После проверки стенд можно остановить: `systemctl stop ruspet-manager-preview.service`. Рабочий сайт/бот продолжат работу.

## Дополнительный CLI

`scripts/test-manager-access.ts` по умолчанию только показывает план выбора. Применение требует `--apply --password-stdin`. Для любой БД, кроме точной `ruspet_manager_preview`, дополнительно обязателен `--working-data`: это создаёт обычный вход к реальному менеджеру и реальные действия на его задачах. По умолчанию этот режим не используется и не предлагается как безопасная песочница. В рабочей БД учебные задачи не создаются. Существующий собственный тестовый вход не сбрасывает пароль при повторе; чужой занятый логин, отключённый вход и участие в пилоте отвергаются.
